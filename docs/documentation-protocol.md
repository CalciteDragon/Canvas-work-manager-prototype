# Documentation protocol

How this repository's documentation is organised, what each part is for, and what an agent
must do to keep it true. [AGENTS.md](../AGENTS.md) is the entry point and points here; this
file is the rulebook. `pnpm docs:check` (part of `pnpm lint`) enforces the structural rules
below, so a broken structure fails the build the way a broken test does.

---

## 1. The map

```text
AGENTS.md                          entry point: orientation, boundaries, working protocol, this map
README.md                          human quickstart: install, run, commands
Canvas Work Manager — … Specification.md
                                   the spec, cited as §N everywhere; design-first, corrected when disproved
docs/
├── documentation-protocol.md      this file
├── architecture/                  the system tree — one folder per system, four files per folder
│   ├── overview.md  why.md  what.md  how.md        level 0: the whole prototype
│   ├── contracts/ domain/ repositories/ mcp-tools/ prototype-data/
│   ├── prototype-host/  ├── api/ mcp-transport/ live-updates/ prototype-runtime/
│   ├── web/             ├── core/ projects/ dashboard/ tasks/ prototype-tooling/
│   └── testing/
├── decisions/                     the §78 decision log, one small entry per answered question
│   └── README.md                  index of every entry, grouped by system, with amendment status
├── roadmap/                       goals, progress and plans — the only place plans live
│   ├── README.md                  how the roadmap works
│   ├── goals.md                   what the prototype is for and what is being pursued now
│   ├── progress.md                the status board (generated between markers)
│   ├── active/                    plans being executed right now
│   ├── planned/                   candidate slices, short, not yet started
│   └── completed/                 frozen records: outcome + definition + plan as executed
├── guides/                        task-oriented how-tos (MCP client setup, the milestone walkthrough)
├── templates/                     the files an agent copies when adding to the structure
└── api/                           GENERATED by `pnpm docs:api` (Compodoc); git-ignored
```

Three kinds of document, three rules of change:

| Kind | Examples | How it changes |
|---|---|---|
| **Living** | `AGENTS.md`, `README.md`, `docs/architecture/**`, `docs/roadmap/goals.md`, `docs/guides/**`, the spec | Edited in the same change as the code. Always describes *now*. |
| **Append-only** | `docs/decisions/*`, `docs/roadmap/completed/*` | Never rewritten. Corrected by an appended, dated **Amended** note or a **Superseded by** banner. |
| **Generated** | `docs/api/`, the board in `docs/roadmap/progress.md` | Never hand-edited. Rebuilt by a script. |

## 2. Principles

1. **Documentation is state, not commentary.** It says what is true now. Prose that
   narrates how something came to be belongs in a completed record or a decision entry.
2. **Same change as the code.** A change that alters a system's behaviour, shape or
   dependencies updates that system's folder in the same commit. "Docs to follow" is a
   defect.
3. **No aspirational documentation.** Nothing is documented as existing before it does. A
   planned thing lives in `docs/roadmap/planned/`, nowhere else.
4. **Frozen means frozen.** A completed record or a decision entry is evidence. If it is
   wrong now, say so *beside* it with a date; do not edit it into agreement.
5. **Link, do not restate.** One fact, one home, everything else links to it. The spec owns
   product intent; a decision entry owns why; a `how.md` owns mechanism; Compodoc owns
   signatures.
6. **Ground every sentence in the repository.** Read the code before describing it. Name
   real files, real symbols, real commands.

## 3. The architecture tree

`docs/architecture/` mirrors the *systems* of the repository, not its folders one-to-one.
A **system** is a part with its own responsibility, boundary and tests: a workspace package,
an app, or a coherent subsystem inside one. The tree today:

- level 0 — the whole prototype (`docs/architecture/`)
- level 1 — the five workspace packages and two runtime apps, plus `testing/` for the cross-cutting
  verification system
- level 2 — subsystems of the host (`api`, `mcp-transport`, `live-updates`,
  `prototype-runtime`) and of the web app (`core`, `projects`, `dashboard`, `tasks`,
  `prototype-tooling`)

### The four files

Every folder has exactly these four files and nothing else. Each answers one question and
nothing another file already answers.

| File | Question | Contains |
|---|---|---|
| `overview.md` | *What is this, in one screen?* | Purpose in two or three sentences; where the code lives; the responsibilities in bullets; links to each subsystem's `overview.md`; links to its own `why`/`what`/`how`. |
| `why.md` | *Why does it exist and why is it shaped this way?* | The architecture-decision view: the problem, the forces, the alternatives rejected, the consequences. Links every `docs/decisions/` entry that shaped it and the spec sections it implements. This is the system-level ADR; individual decisions stay in the log. |
| `what.md` | *What is it made of?* | Diagrams first — Mermaid, C4-style at the top levels (context, container, component), flowcharts or sequence diagrams below — then an inventory of the parts each diagram names. |
| `how.md` | *How does it work and how do I work on it?* | Runtime flow; key symbols with Compodoc links; dependencies in and out with links to the sibling folders; commands to run, test and change it; invariants and lints; where to look first. |

Templates: [`docs/templates/system-*.md`](templates/). Copy all four when you add a folder.

### When the tree changes

| Change in the code | Change in the tree |
|---|---|
| New workspace package or app | New level-1 folder with all four files; link it from `docs/architecture/overview.md`. |
| New subsystem with its own boundary or tests (a new host module, a new feature folder in `apps/web/src/app/features/`) | New folder under its parent, all four files; link it from the parent's `overview.md`. Small features without their own boundary are a bullet in the parent's `overview.md` instead. |
| A system's dependencies change | Its `how.md` **Dependencies** section, and the dependent's. `what.md` if a diagram shows the edge. |
| A public symbol is added, renamed or removed | Its `how.md` **Key symbols** table; `pnpm docs:check` flags a link to a symbol that no longer exists. |
| A decision entry lands | Its system's `why.md` links it (and the decisions index lists it). |
| A system is removed | Delete its folder; remove the link from the parent's `overview.md`; `docs:check` catches the rest. |

### Diagrams

Mermaid, inline, rendered by GitHub and most editors. C4 diagrams use Mermaid's `C4Context`
/ `C4Container` / `C4Component` syntax at the top two levels; below that a plain
`flowchart` or `sequenceDiagram` is clearer. Every node in a diagram is a thing that exists
under the name shown. Keep diagrams small enough to read without zooming; split rather
than crowd.

## 4. Compodoc — the API reference

Compodoc generates `docs/api/` from the whole workspace: Angular components, injectables,
plain classes, interfaces, functions and types across `apps/` and `packages/`. It is
configured by `tsconfig.compodoc.json` at the root (tests, stories and test support are
excluded) and is git-ignored because it is derived.

```bash
pnpm docs:api          # build docs/api/
pnpm docs:api:serve    # build and serve at http://localhost:4320
```

`how.md` files reference public symbols by linking into it with a **relative** path:

| Symbol kind | Path (from `docs/architecture/<system>/how.md`) |
|---|---|
| Angular component | `../../api/components/TaskRow.html` |
| Angular injectable | `../../api/injectables/TaskListStore.html` |
| Plain class | `../../api/classes/TaskService.html` |
| Interface | `../../api/interfaces/TaskRepository.html` |
| Function / const / type | `../../api/miscellaneous/variables.html#createToolRegistry` (also `variables.html#…`, `typealiases.html#…`) |

One more `../` for each level of nesting. `pnpm docs:check` resolves these against the
built pages and their fragment anchors when output exists and, when it does not, checks that the symbol is declared
somewhere in the sources — so a rename breaks the check without anyone running Compodoc.

Doc comments are the source of the reference. When a `how.md` needs a paragraph about a
symbol's contract, the paragraph belongs in the symbol's own `/** … */` comment, and the
`how.md` links to it.

## 5. The decision log

`docs/decisions/` is §78's log: one small entry per answered product or architecture
question, in the §78 shape — **Question / Options tested / What we learned / Current
decision / Confidence / Revisit when** — as bold labels or `##` headings. Name files
`YYYY-MM-<slug>.md`. Template: [`docs/templates/decision.md`](templates/decision.md).

- **Write one whenever a question gets answered**, including questions the code answered
  by accident and you only noticed in review.
- **Never rewrite an entry.** When a later phase changes the answer, append a dated
  `**Amended, YYYY-MM-DD** (…)` paragraph, or put a `> **Superseded by** [entry](…)` banner
  under the title when the whole entry no longer holds. The original text stays as the
  record of what was believed and why.
- **Index it.** [`docs/decisions/README.md`](decisions/README.md) lists every entry under
  the system it shapes, with its status; `docs:check` fails on an unlisted entry.
- **Link it from `why.md`** of the system it shapes.
- **Correct the spec** when the decision disproves it, and say so in the entry.

## 6. The roadmap

`docs/roadmap/` is the only place plans live — high-level goals, the status board, and
one file per slice that moves through three states. Full description in
[`docs/roadmap/README.md`](roadmap/README.md); the short version:

```text
planned/  --start-->  active/  --complete-->  completed/
```

| File | Owner | Changes |
|---|---|---|
| `goals.md` | living | When the direction changes: a milestone closes, the user sets a direction, use of the prototype reorders the candidates. |
| `progress.md` | generated board + hand-written preamble | The board is regenerated by `node scripts/roadmap.mjs sync`; never edit between the markers. |
| `planned/<id>-<slug>.md` | short candidate | Goal, spec sections, sketch of the build, done-when, do-not. No file list, no test plan — those are written when it starts. |
| `active/<id>-<slug>.md` | the one document edited during a phase | The full implementation plan (AGENTS.md step 1), its **Revisions** as reviews change it, and at the end its **Outcome**. |
| `completed/<id>-<slug>.md` | frozen | The record: marker with the closed date and a one-line summary, **Outcome**, the plan as executed. |

Commands (all keep `progress.md` in sync and move files with `git mv`):

```bash
node scripts/roadmap.mjs new 18 calendar --title "Calendar" --summary "Month and agenda views derived from existing dates"
node scripts/roadmap.mjs start docs/roadmap/planned/18-calendar.md
node scripts/roadmap.mjs complete docs/roadmap/active/18-calendar.md --summary "…"   # needs written prose under ## Outcome
node scripts/roadmap.mjs sync                                                         # after any manual edit
```

Rules that keep it from turning into clutter:

1. **One active plan per phase.** Two at once means the phase was scoped wrong.
2. **Planned entries stay short.** They are candidates, not commitments. Detail written
   before a slice starts is detail that will be wrong.
3. **Completed records are frozen.** Their prose is evidence of what was done and thought
   at the time. Later truth lives in `docs/architecture/`; a record that is now misleading
   gets a dated note under its banner, not an edit.
4. **The summary is the contract.** Every plan carries `summary="…"` — one line, what it
   delivers or delivered — and that line is what the board shows. Write it for the reader
   who will never open the file.
5. **Nothing else holds plans.** No plan sections in `AGENTS.md`, no TODO lists in the
   architecture docs, no roadmap in the README.

## 7. Checks

`pnpm docs:check` runs [`scripts/check-docs.mjs`](../scripts/check-docs.mjs), which fails
on any of these; `pnpm lint` includes it.

| Rule | What it catches |
|---|---|
| Every `docs/architecture/**` folder has `overview.md`, `why.md`, `what.md`, `how.md` and no other Markdown | A half-added system; detail files that should be a subsystem |
| Every `overview.md` links each child folder's `overview.md` | An orphaned subsystem |
| Every relative link in `AGENTS.md`, `README.md` and `docs/**` resolves (inline code is not a link; a frozen record's links into source files are not checked, because code moves and records do not) | A moved or deleted target |
| Compodoc pages and fragment anchors resolve (built) or name a declared symbol (unbuilt) | A renamed class still cited in a `how.md` |
| `AGENTS.md` links the entry points (architecture overview, roadmap README/goals/progress, decisions index, this file) | The entry point going stale |
| Roadmap markers well-formed, status matches folder, ids unique, board in sync, completed records have written prose under `## Outcome` | A plan in the wrong state; a stale board |
| `docs/decisions/README.md` lists every entry; every entry has the six §78 sections | An unindexed or malformed decision |
| Templates present | A protocol nobody can follow |

What it cannot catch — and what review must: prose that describes a behaviour the code no
longer has. Reviewers (AGENTS.md step 4) check the touched systems' four files against the
diff.

## 8. Session checklist

**Starting a phase**

- Read `AGENTS.md`, then `docs/roadmap/goals.md` and `progress.md`.
- Read the `overview.md` and `how.md` of every system the phase touches, then the code.
- `node scripts/roadmap.mjs start …` (or `new` first). One active plan.

**During**

- The active plan is the only planning document you edit. Record review rounds in its
  **Revisions**.
- A product question answered → a decision entry, indexed, linked from `why.md`.
- A system's behaviour, shape or dependencies changed → its four files, in the same commit.

**Closing a phase**

- Write the plan's **Outcome** (deliverables, deliberate choices, deviations, deferred,
  open questions — the AGENTS.md step 5 summary).
- `node scripts/roadmap.mjs complete … --summary "…"`.
- Update `goals.md` if the direction moved; update `README.md` if a command or URL
  changed; update the spec if it was disproved.
- `pnpm docs:check`, then `pnpm lint`. Both green before the closing commit.
