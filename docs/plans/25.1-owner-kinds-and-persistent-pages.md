# Slice 25.1 — Distinguish owner kinds and introduce persistent pages

**Status:** in progress.

## Goal

Make `kind: 'root' | 'subproject'` a stored, enforced distinction and give every project a
persisted canonical page that owns its sections, in one schema-version cutover that a bounded
converter carries live data across.

## Spec sections

§11–15 (contracts, storage, persistence behaviour), §26–28 (the two project kinds, pages, the
canvas), §33 (task model, unchanged but re-read), §45 (Clock).

Roadmap: [25-multi-page-projects-overhaul.md](25-multi-page-projects-overhaul.md) §25.1.
Decision:
[2026-09-project-workspaces-and-subproject-work-units.md](../decisions/2026-09-project-workspaces-and-subproject-work-units.md).

## Acceptance check

Concrete and executable, from the roadmap's *Done when*:

1. `pnpm --filter @cwm/prototype-data test`, `@cwm/contracts`, `@cwm/repositories`,
   `@cwm/domain`, `@cwm/mcp-tools`, `@cwm/prototype-host` and `web` test suites are green,
   and `pnpm lint` and `pnpm build` pass.
2. `pnpm prototype:seed nested-projects` writes a v3 document; the host loads it and
   `GET /api/projects` still answers.
3. Running the converter over a **real v2 file** (a copy of the committed
   `prototype/seeds/nested-projects.json` at its pre-cutover revision) produces a document
   that `validateDocumentIntegrity` accepts, preserves every id, every `archivedAt` and every
   section `position`, and is a no-op when run again.
4. A converter run over a document that fails validation leaves the input file byte-identical
   and writes no output.
5. Creating a project through the existing HTTP route yields exactly one canonical page; a
   forced failure during page insertion leaves neither project nor page.

No new navigation, no page-selection API, no shortcut operations — those are 25.2 and 25.4.

## Design decisions this plan makes

Three choices the roadmap left to the phase, recorded here because reviewers will ask.

**A subproject's work canvas is a page record too**, `kind: 'work'`. Page kinds are
`home | work | todos | archive | reflections`. The alternative — sections on a subproject
pointing at no page — would make `pageId` optional and put a branch in every reader. "The
canonical page of a project" is then one lookup: `home` for a root, `work` for a subproject.
`work` is not an optional tab and has no toggle; the capability table, not the UI, is what
says so.

**Root variants declare `parentProjectId: z.undefined().optional()`** rather than omitting the
key. Omitting it makes `project.parentProjectId` a type error on the union at every existing
call site — dozens of them, none of which this phase is about. Declaring it as
`undefined` keeps those reads compiling while a root carrying a parent still fails to parse,
which is the invariant that matters.

**`completedAt` lands on both kinds**, stamped when `status` becomes `completed` and cleared
when it leaves. The roadmap asks for it on subprojects; roots already have a `completed`
status, and giving the same status two different meanings by owner kind would be a worse rule
than the one it replaces. This is a timestamp, not a capability, so it does not breach
"preserve existing root settings".

### Repositories — `packages/repositories/src`

| File | Responsibility |
|---|---|
| `interfaces.ts` | `ProjectPageRepository` (find/list/insert/update). No `remove`: a page is never deleted this phase |
| `json-repositories.ts` | `JsonProjectPageRepository` over the `projectPages` collection, filtering by `projectId`/`kind`/`enabled` |
| `data-store.ts` | integrity rules, below |

Integrity rules added to `validateDocumentIntegrity`:

- every page's project exists and is in the page's own workspace
- a page's kind agrees with its owner's kind: `home` and the optional kinds only on roots,
  `work` only on subprojects
- exactly one `home` per root, exactly one `work` per subproject, at most one of each optional
  kind per root
- `home` and `work` are always `enabled: true`
- every section's `pageId` exists, belongs to the section's project, and names a page kind
  that accepts sections
- a root never carries `parentProjectId` (already enforced by the schema; asserted here too,
  because a hand-edited file reaches this function through paths the schema union would have
  rejected only at parse)
- shortcut placements, if any exist, reference a live destination page and a source section in
  the same workspace. The collection is empty in every document this phase writes; the rules
  exist so 25.4 does not land them on a document already in the field

### The converter

`upgradeProjectPages(document: unknown): { document, changed }`.

- v3 in → returned unchanged, `changed: false` (idempotent).
- not v2 and not v3 → throws naming the version it found.
- v2 in → every project without `parentProjectId` becomes `kind: 'root'` and gains a `home`
  page; every project with one becomes `kind: 'subproject'` and gains a `work` page; every
  section gains the `pageId` of its project's new page. Ids, names, configs, positions,
  `archivedAt`, `archivedWithSectionId` and timestamps are copied through untouched. Page ids
  are derived deterministically from the project id so a re-run of the same input produces the
  same document.
- The result is validated with `validateDocumentIntegrity` **before** anything is written.

The CLI writes `<path>.backup-<timestamp>.json` first, then writes through a temp file and
rename, the same way `seed-cli.ts` does. On any failure it writes nothing and exits non-zero.

This is one converter for one cutover. It is not a migration framework, and nothing registers
it in a chain.

## Boundaries touched

- **Domain depends on repository abstractions only** (§12). `ProjectService` gains a
  `ProjectPageRepository`, not a service. No new service edge exists in either direction, so
  the graph stays acyclic; `SectionService` still holds repositories and never a row service.
- **No `new Date()` in domain** (§45). `completedAt` comes from the injected `Clock`, which the
  existing lint rule already enforces and test 18 pins.
- **Contracts defined once** (§11). Page kinds, capabilities and the shortcut placement shape
  live only in `packages/contracts`; the converter, the repositories, the domain and the seeds
  all import them. The converter deliberately does **not** re-declare the v2 shape as a Zod
  schema — it reads the untyped input and validates only the *output*, so there is no second
  definition of anything current.
- **Deliberately disposable** (§71). The converter and its CLI are one bounded file each. No
  migration registry, no version chain, no rollback framework.
- **Angular untouched** except the fake gateway fixture, which is test support.

## Explicit non-goals

Deferred to their own slices, and not to be reached for here:

- page selection, filtering, toggling, or any page operation — 25.2
- shortcut *operations*; only the placement schema and an empty collection land here — 25.4
- archived-ancestor visibility rules across read models — 25.2
- routing, the secondary sidebar, subproject canvases, description/due-date UI — 25.3
- Todos, Archive and Reflections page renderers and services — 25.5–25.7
- MCP schema/description changes for root vs subproject creation — 25.2
- permanent deletion, bulk restore, root/subproject conversion, subtree moves across roots
- any general migration framework

## Open questions

None blocking. Two noted:

- **`ordered(projectId)` stays project-scoped.** Every project in a v3 document has exactly one
  section-bearing page, so project-scoped and page-scoped ordering are the same set. 25.2
  makes it page-scoped when a second such page can exist; doing it now would be untestable
  scope creep.
- **The old `UpdateProjectInput.parentProjectId` reparenting path** survives for subprojects
  only. Whether reparenting is wanted at all is a 25.3 UI question; this phase keeps the
  existing capability rather than removing behaviour a test currently protects.
