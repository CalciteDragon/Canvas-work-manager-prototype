# Slice 25.1 — Distinguish owner kinds and introduce persistent pages

**Status:** done. Verified by `pnpm test` (1332), `pnpm lint`, `pnpm build`, and by converting and using the real `.prototype/data.json` in the browser and over HTTP.

## Goal

Make `kind: 'root' | 'subproject'` a stored, enforced distinction and give every project a
persisted canonical page that owns its sections, in one schema-version cutover that a bounded
converter carries live data across.

project kinds, pages, the canvas), §33 (task model, unchanged but re-read), §45 (Clock).

No navigation, no page-selection API, no shortcut operations — 25.2, 25.3 and 25.4.

## Design decisions this plan makes

**A subproject's work canvas is a page record too**, `kind: 'work'`. Page kinds are
`home | work | todos | archive | reflections`. The alternative — sections on a subproject
pointing at no page — makes `pageId` optional and puts a branch in every reader. "The canonical
page of a project" is then one lookup: `home` for a root, `work` for a subproject.

`work` is deliberately **not** the fifth kind the decision entry's *Revisit when* set a
tripwire for. That tripwire is about a growing menu of pages a person can enable; `work` cannot
be added, disabled, chosen or navigated to. The decision entry now says so in its own words,
and §26 lists it separately from the four navigable kinds.

**Root variants declare `parentProjectId: z.undefined().optional()`** rather than omitting the
key, so `project.parentProjectId` keeps compiling across the union at the ~dozen existing read
sites (`data-store.ts:116–120,251`; `project-service.ts:78,124,130,197–198`;
`json-repositories.ts:78`; `seeds.ts:59`; `fake-gateway.ts:78`; `sub-projects-store.ts`;
timeline and workspace services) while a root carrying a parent still fails to parse. Verified
by running it against the pinned zod 4.4.3 and by `tsc`.

The **`null` path needs its own answer.** `UpdateProjectInput.parentProjectId` is
`.nullable()`, and `ProjectService.update`'s `apply` *deletes* the key on `null` — today that
promotes a subproject to a root. Under the union it would instead surface as a raw `ZodError`
out of `commit`. `parentProjectId` therefore **stops being nullable** in
`UpdateProjectInputSchema`, and the service refuses a kind change explicitly with a
`DomainRuleError` before it reaches `ProjectSchema.parse`. Promotion and demotion are
root/subproject conversion, which the roadmap lists as a non-goal.

**`completedAt` lands on both kinds**, stamped when `status` becomes `completed` and cleared
when it leaves. Recorded in the decision entry as well as here, because plans are archived and
the roadmap asked for a justification.

- a page's project exists and shares its workspace

### The converter

`upgradeProjectPages(document: unknown): { document: PrototypeDocument; changed: boolean }`.

- v3 in → returned unchanged, `changed: false`.
- neither v2 nor v3 → throws naming the version found.
- v2 in → no `parentProjectId` becomes `kind: 'root'` + a `home` page; with one becomes
  `kind: 'subproject'` + a `work` page; every section gains its project's new `pageId`. Ids,
  names, configs, positions, `archivedAt`, `archivedWithSectionId` and timestamps copy through
  untouched. Page ids derive deterministically from the project id, so re-running the same
  input yields the same document.
- The result goes through `validateDocumentIntegrity` **before** anything is written.
- A v2 project with **no sections** still gets its page — `nested-projects`' "Cabinets" is
  exactly this case and is already pinned by `seeds.test.ts`.

The CLI writes `<path>.backup-<timestamp>.json`, then the target through temp-file-and-rename,
the way `seed-cli.ts` does. On any failure it writes nothing and exits non-zero.

One converter for one cutover. No registry, no version chain, no rollback framework.

## Boundaries touched

- **Domain depends on repository abstractions only** (§12). Both services gain a
  `ProjectPageRepository`, not a service. Graph stays acyclic — verified against
  `section-service.ts` (repositories only) and `task-service.ts`/`reflection-service.ts` (both
  compose `SectionService`).
- **No `new Date()` in domain** (§45). `completedAt` comes from the injected `Clock`;
  `time-lint.test.ts` and `scripts/check-no-direct-date.mjs` already guard it.
- **Contracts defined once** (§11). Page kinds, capabilities and the shortcut shape live only
  in `packages/contracts`. The converter reads untyped input and validates only its *output*,
  so it declares no second copy of the v2 shape.
- **Dependency direction.** Moving `@cwm/repositories` into `prototype-data`'s `dependencies`
  is the fix, not the violation: `scripts/check-package-imports.mjs` only scans the domain, so
  nothing would have caught a production import of a dev dependency until `pnpm build`.
- **Duplicated rules, knowingly.** `fake-gateway.ts`'s `applyProjectUpdate` already
  reimplements `ProjectService.update`'s field application. It has to learn immutable `kind`
  and derived `completedAt`. Noted so it is updated deliberately rather than discovered.
- **Deliberately disposable** (§71). One converter, one CLI. No migration framework.

## Explicit non-goals

- page selection, filtering, toggling, any page operation — 25.2
- shortcut *operations* and shortcut integrity rules — 25.4
- archived-ancestor visibility across read models — 25.2
- routing, secondary sidebar, subproject canvases, description/due-date UI — 25.3
- Todos, Archive, Reflections renderers and services — 25.5–25.7
- richer MCP tool descriptions for the two kinds — 25.2 (the schema rewrite is unavoidable here)
- page agreement on section reassign — 25.2
- permanent deletion, bulk restore, root/subproject conversion, subtree moves across roots
- any general migration framework

## Open questions

None blocking. One noted: **`ordered(projectId)` stays project-scoped.** Every v3 project has
exactly one section-bearing page, so project-scoped and page-scoped ordering are the same set.
25.2 makes it page-scoped when a second such page can exist.

## Revisions

- **Review round 1** returned findings in every category, all substantive, all incorporated.
  The three largest were things the plan had asserted without checking: `create_project`'s MCP
  input schema calls `.omit()` on what is about to become a discriminated union, which is a
  hard break this phase cannot defer; two *production* Angular call sites create projects and
  so need a `kind`, contradicting the plan's claim that Angular was untouched; and
  `@cwm/repositories` is a `devDependency` of `prototype-data`, which the converter's
  production import would violate. The review also corrected the domain test paths
  (`src/`, not `test/`), removed `apps/e2e/seed.ts` (it constructs nothing), removed
  `ProjectPageQuerySchema` and the shortcut integrity rules as creep, supplied a
  failure-injection mechanism for test 14 where the package has no idiom to copy, caught that
  the existing cycle test's setup becomes invalid under the union, caught the `parentProjectId:
  null` promotion path the union would turn into a raw `ZodError`, and pointed out that
  acceptance item 3's "pre-cutover v2 file" is unreachable once this same change regenerates
  the seeds — hence the committed v2 fixture. It also found that the decision entry's "can
  never own pages" and its fifth-page-kind tripwire had gone stale against §26; both are
  corrected in the decision entry itself.

- **Review round 2** confirmed every round-1 fix landed correctly — the MCP union typechecks
  because TypeScript distributes an object spread over a union, `ProjectGateway.create` is a
  type alias over the contract and needs no textual change, nothing else calls `.omit`/`.extend`
  on `CreateProjectInputSchema`, no caller anywhere passes `parentProjectId: null`, and test
  14's rollback is observable because `runUnitOfWork` only commits after `fn()` returns. What
  it found instead were file-list gaps that would each have stopped a build:
  `validateDocumentIntegrity` is not in the `@cwm/repositories` barrel, which the converter
  needs; `api/services.test.ts` and `mcp/handler.test.ts` both build the `Persistence` bundle
  as a literal; two dev-panel specs construct `Project` literals; and both harnesses must
  actually construct and wire a page repository, not merely emit pages. It also corrected two
  factual errors in the plan's prose — `buildHarness` does expose its repositories, and test
  16's existing setup fails the *type check* rather than at commit — pinned the canonical page
  id to `ids.next('projectPage')`, flagged that the `create` test helper's `overrides = {}`
  stops compiling for ~20 tests, and noted that `document.ts`'s "no migration runner" comment
  and the load-time error message both go stale the moment the converter lands.

- **Diff review** (correctness, and boundaries/documentation as separate passes) returned four
  substantive findings, all of which held and all fixed in `bc2f01e`. The most serious was the
  living-documentation one: the spec's own inline "planned in slice" footnotes still described
  25.1 as unbuilt, in the very change that built it. The most interesting was a test that could
  not fail — the backup-ordering case asserted only that the backup path appeared among the
  written paths, so it would have passed with the writes reversed; it now records call order,
  and that was checked by reversing the implementation and watching it fail. The review also
  caught that `applyProjectUpdate` in the fake gateway shipped unchanged despite this plan
  flagging it, and that one test's title claimed more than it exercised. The boundaries pass
  returned nothing: no new service edge, the page repository is a genuine interface, and the
  `@cwm/repositories` dependency move is complete.
