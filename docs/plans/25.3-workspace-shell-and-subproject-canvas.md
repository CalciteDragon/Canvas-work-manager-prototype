# Slice 25.3 — Secondary sidebar, Home and single-page subprojects

**Status:** in progress.
**Roadmap:** [25-multi-page-projects-overhaul.md](25-multi-page-projects-overhaul.md) §25.3.
**Depends on:** 25.2 (done) — `ProjectPageService`, `pageId` on every section, page-scoped
`SectionService.list`, `pages` on the gateway, `rootProjectId` on `LiveEvent`.

## Goal

Give a root project a navigable second column with its required Home, and give a subproject
its sole work canvas with the work metadata §26 asks for — so a unit of work three levels deep
is reachable, editable and never loses its root context.

## Spec sections

§19–20 (page → store → gateway, no mega-store), §21 (tokens), §23 (the project navigation
column), §26 (structure, two kinds of project, pages), §27 (ownership chain, canvases),
§28 (flow/grid), §29–32 (registry, capability table, frame, edit layout mode), §62 (live
updates), §63 (optimistic UI), §65–66 (feature structure), §68 (route map), §69 (testing).

## Acceptance check

Executable form of the roadmap's *Done when*:

1. `pnpm test`, `pnpm lint`, `pnpm build` and `pnpm storybook:build` green; `pnpm e2e` still
   green with **no edit to `apps/e2e`**.
2. On the `nested-projects` seed, in a browser: open the root `project-renovation` → the column
   renders flush beside the global sidebar with Home and the root's live subproject tree; open
   `project-cabinets` — the deepest chain is `renovation → kitchen → cabinets`, so three levels
   counting the root — → the column stays, breadcrumbs list both ancestors, its own work canvas
   renders. Only the root is seeded with a Sub-Projects section (`seeds.ts:394`; `cabinets`
   deliberately has no sections at all, `:388–391`, and `packages/*` is a non-goal here), so the
   nested-create step is: enter Edit Layout Mode on `project-kitchen`, Quick-add a Sub-Projects
   section, create a child from it, and open the child.
3. Every registered section type mounts a frame on a root's Home **and** on a subproject's work
   canvas (test 14 iterates `SECTION_REGISTRY`); flow/grid, edit layout mode, container
   reassignment and rejected-drop rollback still pass their existing cases on the extracted
   canvas.
4. `/projects/:id/pages/home` survives reload, Back and Forward (tests 10–11). Deep links to an
   enabled-but-unrendered kind, a disabled kind, `/pages/work` on a root, and `/pages/home` on a
   subproject each land on the correct canvas with a visible explanation and a replaced URL.
5. Scrolling a long canvas leaves the column in place; at ≤ 60rem it collapses behind a labelled
   `<button>`; its links are reachable by Tab and carry `aria-current`. Verified in the browser
   at 900px and by tests 16–18.
6. Storybook renders `ProjectPageNavigation` (root, subproject-with-breadcrumbs, collapsed) and
   `ProjectCanvas` (flow, grid, edit-layout, empty).
7. Todos, Archive and Reflections appear in no navigation, no tab list and no control.

## Design decisions this plan makes

Stated here so implementation does not re-open them. Two rounds of plan review are folded in;
see Revisions.

**§26's order is the layout: Header, then Navigation and Controls, then Canvas.** The project
header is a property of the *project*, not of Home, so `ProjectWorkspaceShell` renders it once,
spanning above the column and the canvas. Were it to stay inside a page renderer, a root's name,
status and More menu would vanish the moment 25.5's Todos renderer mounted, and 25.5–25.7 would
each re-implement it.

**The column lives in the projects feature; the shell contributes one CSS rule.** State stays
out of `ShellStore` — loading a root's pages and walking ancestors in the one store every route
pays for is precisely §20's mega-store. Placement is fixed in CSS instead:
`.workspace:has(> [data-flush-workspace]) { padding: 0; }`, with `ProjectWorkspaceShell` setting
`data-flush-workspace` as a host attribute. Keyed on a declared hook rather than on the
component's selector, so a rename cannot silently stop matching. `app-shell.ts`, `app-shell.html`,
`shell-store.ts` and the whole of `sidebar/` are **unchanged** — §23: "the global sidebar stays
where it is; the project column is additional".

*Rejected alternative:* move the gutter out of `.workspace` entirely and give each routed page
its own padding. Cleaner in principle and it deletes the special case, but it edits seven
feature pages for a phase that touches one of them, and it would put an unrelated visual
regression risk on `/app`, `/calendar`, `/search` and `/settings`. Revisit if a second
full-bleed route appears.

**The geometry, drawn once so it is not two pictures.** §23's diagram and §26's structure list
disagree about where the header sits; §23 wins, because it is the one describing the *shell*.
The shell's grid is two tracks — `var(--layout-project-column-width)` and `minmax(0, 1fr)` —
and the navigation column occupies the first for the full height of the workspace region, flush
against the global sidebar at x=0. The project header, the fallback notice and the routed
renderer stack inside the **second** track:

```text
┌─────────┬──────────┬─────────────────────────┐
│ Sidebar │ Project  │ Project header          │
│         │  Home    │ ─────────────────────── │
│         │  ──────  │ Controls                │
│         │  Work ▸  │ Section canvas          │
└─────────┴──────────┴─────────────────────────┘
```

§26's "Project Header / Project Navigation / Controls / Section Canvas" is read as the page's
parts, not as a strict vertical stack — the header is still rendered once per project by the
shell, which is the property that keeps 25.5–25.7 from re-implementing it. Recorded in the
decision entry beside the §20 one.

**The canvas track, not `.workspace`, carries the gutter.** With `padding: 0` on the workspace,
the second track is padded with `--space-5` and the navigation track stays flush, which is the
point of the rule. The column is `align-self: start` with
`max-height: calc(100vh - var(--layout-top-bar-height))`, its own `overflow: auto` for a deep
tree, and `position: sticky; top: 0` inside `.workspace`'s scrollport — a stretched grid item
has no sticky travel, so `align-self` is load-bearing, not decoration.

**Resolution is a positive rule, not three refusal cases.** A `/pages/:kind` URL renders that
page only when *all* of: the project is a root; `isNavigablePageKind(kind)` (so `work` is never
addressable); a page record of that kind exists and is `enabled`; and `PROJECT_PAGE_REGISTRY`
has a renderer. Anything else redirects. The registry therefore holds **only navigable kinds** —
one entry, `home`, in this slice — and a subproject's canvas is chosen from `project.kind`.

**Fallbacks redirect with `replaceUrl` and carry their reason in navigation state.** The notice
travels as `router.navigate(..., { replaceUrl: true, state: { pageNotice } })`. It is read from
`Location.getState()` **inside the same effect that resolves the page**, not on init — the two
fallback cases behave differently and one code path has to cover both: `/pages/todos` →
`/pages/home` stays inside one route config, so Angular reuses the component and it never
re-inits, while the subproject case crosses three segments to two, destroys the component and
takes any store field with it. Reading from location state in the resolve effect covers reuse,
re-creation and reload alike. Cleared on the next successful resolve that carries no notice.

**Quick Add moves from the project header to the canvas controls row**, still gated by §32's
Edit Layout Mode. A root has several canvases and one header; "add a section" acts on a canvas.
§26's header list is amended in this change, with a decision entry (AGENTS.md §2 rule 5). The
`data-project-quick-add` hook and its edit-mode gate are preserved so `apps/e2e` is untouched.

**Two page reads, deliberately.** `pages.list(rootId)` supplies the column; `pages.list(projectId)`
supplies the canvas's own `pageId` — on a subproject these are different projects and the second
is the only source of the `work` page id. When `projectId === rootId` the first answer is reused.

**Navigation excludes archived projects**, using the non-archived status filter `ShellStore`
already applies, because §31 says archived work does not appear in ordinary views. Breadcrumbs
are built from `projects.get` on the ancestor chain rather than from that filtered list, so
standing on an archived project — which §31 says must still render — does not break its own
breadcrumb. This is the third store issuing a workspace-wide project list per navigation
(`ShellStore`, `SubProjectsStore`, and now `ProjectWorkspaceStore`); acceptable under §3.1 and
noted rather than hidden.

**`subproject-page.{ts,html,scss}` is not created.** With the header in the shell, a root's Home
renderer and a subproject's work renderer would differ in nothing; `ProjectCanvas` is both. The
kinds differ in their *header*, which `ProjectHeader` varies on `project.kind`. Deviation from
the roadmap's file list, stated rather than smuggled — 25.7 may earn a distinct work-unit
renderer and can add it then.

## The store split, specified

`ProjectPageStore` today owns both halves of a project page, and they are coupled. This section
is the contract for pulling them apart; it exists because round 2 showed the coupling is where
this phase can go subtly wrong.

**`ProjectWorkspaceStore` (new, provided by the shell)** takes: the project record, the ancestor
chain, `pages`, `navPages`, `subprojectTree`, `resolvedPageId`, `progress`, `writeError`,
`projectWritePending`, and the project writes `rename`, `setStatus`, `setDescription`,
`setTargetDate`, `archive`. It takes `refreshProgress` with it, and with it the `pendingWrites`
/ `projectRefreshQueued` machinery, which existed to stop a project re-read from clobbering an
optimistic project write. It registers every async operation with `PendingTasks`, as
`ProjectPageStore` does today — without it `fixture.whenStable()` resolves before `pages.list`
lands and tests 1–13 become flaky in a way that reads as a product bug.

**`ProjectPageStore` (kept, provided by `ProjectCanvas`)** takes: `sections`, page identity, the
removal prompt, `canvasRevision`, `projectDataRevision`, `projectHierarchyRevision`, `editMode`,
`loading`, `error`, `sectionError` and every section write.

`refreshProject()` is **narrowed, not deleted**. Round 3 was right that the earlier wording was
wrong on both counts: `project-page-store.ts:231–270` reads `projects.get` *and*
`sections.list`, and it is the only path that re-reads the canvas on a live frame (`:189–194`)
and on reconnect (`:213–220`) — `project-page-store.spec.ts:879` asserts exactly that. It
becomes `refreshSections()`: the same quiet, generation-guarded, self-requeueing loop over
`sections.list(projectId, { pageId })`, with the `projects.get` call and the project-record
writes removed.

Its deferral counter stays with it too, for the same reason: its own comment (`:90–105`) names
**`moveSection`** as the hazard — an optimistic reorder that a live frame would repaint at the
pre-write value — and `project-page-store.spec.ts:896` is a pure canvas test of it. It is
renamed `pendingSectionWrites` for what it now guards. `projectWritesState` /
`projectWritePending` (`:110–122`) is the *other* counter and moves to the workspace store
whole, since it exists for the Restore guard the header now drives.

**Staleness guards.** Today's predicate is `projectState()?.id === projectId`
(`project-page-store.ts:345,356,385,663,692`), which also doubles as "is anything loaded". With
the project record gone, the canvas store guards on `requestedProjectId`, `requestedPageId`,
`loadGeneration` and an explicit `loadedState` boolean. The sections signal cannot serve as
"loaded" — an empty canvas is a legitimate state (`project-page.html:148`).

**Mount ordering.** `pageId` now needs a second round trip (`projects.get` → `pages.list` →
`sections.list`). The shell renders the outlet only inside `@if (resolvedPageId(); as pageId)`;
an `input.required<ProjectPageId>()` handed `undefined` throws.

**Errors and the loading hook.** `data-project-loading` moves to the **shell**, which is what is
in flight during `projects.get` → `pages.list` while the outlet has not mounted; `apps/e2e` never
uses that hook, so it is free to move. `data-project-error` exists in both: the shell's for an
unreadable project, the canvas's for a failed section list. Today's sequential load — project
first, so an unreadable project fails as "not found" rather than racing the section list — is
preserved by the shell resolving `pageId` before the canvas mounts at all. `data-project-write-error`
(`project-page.html:94–96`) belongs to the header, so `ProjectHeader` takes a `writeError` input
alongside `project` and `progress` — it stays presentational, it just renders one more input.

**Two loose ends in `ProjectPage` that the split must land somewhere.** `drop()` reads
`store.project()?.id` twice (`project-page.ts:145,150`) to decide whether to remount the canvas
after a rejected drop; it uses the `projectId` input instead. And one
`(document:keydown.escape)` host listener closes *both* popovers (`project-page.ts:49`); Quick
Add's menu is now the canvas's and More's is the header's, so each owner declares its own
listener for its own menu.

**`addSection` sends `pageId` explicitly.** It omits it today (`project-page-store.ts:334–341`)
and leans on canonical-page resolution, which is right for Home and a work canvas and wrong the
moment a second section-bearing page renders. §27's rule is "a page supplied — resolve there", and
the canvas knows its page. `project-page.spec.ts:206` asserts the exact `sections.create`
argument and is updated with it.

**Live updates (§62), three distinct rules.** Both stores subscribe; the halves are disjoint, so
a reconnect issues each read once rather than twice.

| What | Matches on | Store |
|---|---|---|
| header progress | `event.projectId === projectId` — any frame, including `task.*` | workspace |
| the project record | `project.*` **and** (`event.projectId === projectId` or `event.entityId === projectId`) | workspace |
| column tree and breadcrumbs | `project.*` and `event.rootProjectId === rootId` | workspace |
| canvas data-revision bump (each container re-reads itself off it) | `event.projectId === projectId` — any frame | canvas |
| canvas hierarchy-revision bump (a Sub-Projects section re-reads off it) | `project.*` — **any** project, which is today's rule at `project-page-store.ts:178` and what case `:765` asserts: a sibling's creation must move this canvas's hierarchy view | canvas |
| quiet `refreshSections()`, deferred while `pendingSectionWrites > 0` | `project.*` **and** `event.projectId === projectId` — the gate today's `:191` already applies, kept so a `task.*` frame does not issue a `sections.list` | canvas |
| everything | `prototype.reloaded` — loud reload in both | both |

`rootProjectId` is right for the tree and wrong for progress: a task written in a sibling
subproject three levels away must not re-read this project's record on every frame, and today's
`refreshProgress()` on any same-project event (`project-page-store.ts:190`) must not be narrowed
to `project.*`, or an agent completing a task stops moving the header percentage.

**Canvas → shell.** `NgComponentOutlet` binds **inputs only**; it has no output API. The canvas
therefore receives `onProjectDataChange` and `onProjectHierarchyChange` as **callback inputs**
with class-property-arrow identity, delivered through a `computed()` inputs record — exactly the
mechanism and the reason documented at `project-section-frame.ts:68–94`. The plan's earlier
"output" wording was wrong.

**Shell → canvas.** Outlet inputs are `projectId`, `pageId`, `projectLayoutMode` (the canvas
renders §28's flow/grid and applies §47's `gridProjectLayout` flag), `restoreBlocked`,
`onProjectDataChange`, `onProjectHierarchyChange`.

## Test plan — written first

Vitest + `TestBed` with `FakeWorkManagerGateway`, `FakeLiveUpdates` and — new to this feature —
`RouterTestingHarness`, which today appears only in `app.routes.spec.ts:36`. Two harness facts
the plan commits to rather than discovering mid-implementation:

- **`provideLocationMocks()`** (`@angular/common/testing`) is required in the shell spec's
  TestBed. `shell-test-providers.ts:49` uses `provideRouter([])` with no location mock, so
  `Location.back()`/`forward()` would hit jsdom's real history asynchronously. `SpyLocation`
  makes `replaceState`, `back()`, `forward()` and `getState()` synchronous, which is exactly
  what tests 9–11 need.
- **`FakeWorkManagerGateway.projects.list` ignores its query** (`fake-gateway.ts:96`), so no
  rendered assertion can prove the archived filter. The repo's idiom for that is
  `argumentTo('projects.list')` (`shell-store.spec.ts:98`), and tests 7 and 29 use it. The fake
  is otherwise sufficient: per-project `pagesOf` with a canonical fallback (`:79–93`),
  `sections.list` honouring `pageId` (`:224–234`), `completedAt` derived on status change
  (`:391–392`). `failOn` keys on method name alone, so test 13's `failOn: {'sections.list': …}`
  fails the Archived region's read too — the spec expects both surfaces rather than one.

## Boundaries touched

- **Components depend on gateway interfaces only** — the two stores inject
  `WORK_MANAGER_GATEWAY`; `ProjectPageNavigation` and `ProjectHeader` inject nothing, like
  `Sidebar`.
- **No mega-store (§20)** — `ProjectWorkspaceStore` is provided by the routed shell and dies
  with it; `ShellStore` is untouched. This is why placement was solved in CSS.
- **Tokens only (§21)** — `--layout-project-column-width` joins `--layout-sidebar-width`; the
  sticky column's `max-height` is computed from `--layout-top-bar-height`; no literal colors,
  spacing or radii anywhere new.
- **Contracts defined once (§11)** — `ProjectPageKind`, `isNavigablePageKind` and
  `canonicalPageKindFor` come from `@cwm/contracts`; the registry adds a renderer and a label
  and never re-enumerates the kinds.
- **No domain, host or MCP change** — page resolution is a rendering decision over records the
  domain already returns.
- **e2e selectors preserved** — the hooks `apps/e2e` actually uses: `data-project-name`,
  `data-project-status`, `data-layout-edit-toggle`, `data-project-quick-add`, `data-add-section`,
  `data-section-frame`, `data-quick-create`, `data-task-row`, `data-section-remove*` and the
  `data-archived-*` region hooks keep their names, their edit-mode gates and their relative
  order. `data-project-loading` is the one hook that moves (to the shell); nothing in `apps/e2e`
  references it.

## Explicit non-goals

- Shortcut placements on Home — 25.4.
- Todos, Archive and Reflections **renderers**, and any navigation that advertises them —
  25.5–25.7. `archived-region` stays on every canvas until 25.6 replaces it.
- A UI for enabling or disabling optional pages, and the **Open archive** control — 25.6.
- §26's *"A URL pointing at a disabled page falls back to Home, says why, and offers to
  re-enable it."* The first two clauses ship here; **the re-enable offer is deferred to 25.6**,
  because re-enabling a page whose renderer does not exist yet returns the user to the same
  fallback. Named so the deferral is a decision, not an oversight.
- Any change to `packages/*` or `apps/prototype-host`. If this phase needs one, that is a
  finding to raise, not a file to edit.
- Mobile layout beyond §23's collapse; the prototype is desktop-first.

## Open questions

1. **Does `/projects/:id` stay valid for a root, or redirect to `/pages/home`?** It **stays**,
   rendering Home: §68 lists both routes, and the sidebar, project creation and every
   Sub-Projects link use the short form. Test 2 pins the consequence.
2. **Direct children or the whole hierarchy in the column?** §23 says "the root's subprojects as
   the work hierarchy" — recursive, non-archived.
3. Nothing here changes the shape of the work enough to need the user.
