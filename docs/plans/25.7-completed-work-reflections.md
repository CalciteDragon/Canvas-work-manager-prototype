# Slice 25.7 — Reflections for completed work

**Status:** planning complete, ready to implement against. Three review rounds ran — two paired, one combined; the third returned only text-level findings, all applied. See **Revisions**.

## Goal

Let a reflection optionally name the completed task or sub-project it is about, and give a root an optional **Reflections** page that aggregates the whole tree's journal newest-first beside a picker of completed work to write about.

## Spec sections

Implements §36 ("Reflecting on completed work", "The Reflections page") with §11–12, §45, §52–55 and §62–63; integrates with §19–23, §26–27, §30–31, §34, §61 and §68–69. Preserves boundaries §8–15, §21, §45, §70–71 and §80; closure follows §77–79.

Sources: [parent roadmap](25-multi-page-projects-overhaul.md), [settled project/page rules](../decisions/2026-09-project-workspaces-and-subproject-work-units.md), [sections own their data](../decisions/2026-09-sections-own-their-data.md), [what undo means](../decisions/2026-09-what-undo-means-for-an-archived-row.md), [disabled-page semantics](../decisions/2026-09-a-disabled-page-hides-navigation-not-data.md), [optional pages are created on first enable](../decisions/2026-09-optional-pages-are-created-on-first-enable.md), and 25.5's [chronology and canonical navigation](../decisions/2026-09-todos-chronology-and-canonical-navigation.md).

## Repository grounding

**The reflection write path**

- `ReflectionSchema` has no subject. It carries `sectionId`, `archivedAt` and `archivedWithSectionId`, so ownership, archiving and cascade undo are settled and this slice must not touch them.
- `ReflectionService` composes `SectionService` and `ProjectRepository`. It has **no** task dependency. `assertSectionLive` uses `sections.requireWithin`, and `assertProjectWritable` takes a repository rather than a service, both so a `reflections.write`-only agent needs no read grant for a write's own lookups. Subject validation must follow the same rule, which is why it takes `TaskRepository` and not `TaskService`.
- `ReflectionService.update` builds `next` from `current` and short-circuits on `JSON.stringify` equality — it is written to tolerate callers echoing stored values.
- `SectionService.resolveContainer` returns the live container on the resolved page **or creates one** (`existing ?? this.addWithin(...)`). An agent naming only a `pageId` does not fail on an empty Reflections page — it creates the container. Any claim about "naming the container" is a claim about the page's own composer, not the write path.
- `assertPermitted` short-circuits for non-agent actors (`if (actor.actor !== 'agent') return;`), and a user's `ActorContext` types `permissions?: undefined`. Any predicate form must mirror that, or every person's refusal message degrades to the agent-safe one.
- `apps/prototype-host/api/errors.ts` maps `EntityNotFoundError` → **404 `not_found`** and `DomainRuleError` → **409 `rule_violation`**. The error *class* is a channel, and the file already says so for `AgentAuthenticationError` ("a 401 is never an oracle") and for foreign sections ("409 would confirm it exists").
- `ReflectionService.assertProjectVisible` deliberately answers `EntityNotFoundError` for a foreign-workspace project: missing and foreign are indistinguishable by design, and `harness.ts`'s `FOREIGN_PROJECT` fixture states the rule.
- `ProjectService.assertParentIsUsable` guards self-parenting and cycles only — it does **not** confine a reparent to the current root tree — and `UpdateProjectInputSchema` permits `parentProjectId`. `validateDocumentIntegrity` runs on **persist** as well as load. So any load-time invariant about tree membership can abort an unrelated, legal write.

**Reads and ordering**

- `TaskRepository.list` excludes archived rows unless `TaskQuery.includeArchived` is true; `ProjectTodosService` relies on exactly that. The workspace project list, by contrast, is read complete.
- `ProjectStatusSchema` is one enum holding both `completed` and `archived`, so a project cannot be both. A task carries `status` plus a separate `archivedAt`, so it can.
- `ReflectionService.list` sorts with `localeCompare` on `createdAt` and `id`. `ProjectTodosService` rejects that comparator by name — *"Ordinal, never `localeCompare`: a collation that sorts ids by locale is not a chronology"* — and normalises ISO second/fraction forms through a private `instantOf`, because `10:00Z` and `10:00:00.0Z` are one instant raw text comparison calls two.
- `ReflectionsStore.startRead` then **re-sorts in the browser**: `[...items].sort((a, b) => b.createdAt.localeCompare(a.createdAt))` — locale collation, no id tie-break, no fraction normalisation. It is the order a canvas container actually renders. `apps/web` depends on `@cwm/contracts` only, not `@cwm/domain`.
- `ProjectTodosService` and `ProjectArchiveService` are the precedents for a derived root projection: repository-only dependencies, `assertPermitted` for **every** category before any content read, `EntityNotFoundError` for a missing/foreign root, `DomainRuleError` for a sub-project root, empty result for an archived root, `archivedAncestry` for descendant exclusion, `nameOf(section)` for display names, ids-and-names but never routes. `ProjectTodoItemSchema` is a discriminated union precisely so no reader guesses which fields are present.
- `ReflectionService.list` has exactly one existing order assertion (`toEqual([second.id, first.id])`), which stays green under an ordinal comparator. Nothing existing pins the change.

**Pages, transports and fixtures**

- `TodosGateway` and `ArchiveGateway` are each a **dedicated top-level seam** with one `get(projectId)`. `WorkManagerServices` keys them `todos` and `archive` beside `reflections: ReflectionService`.
- `get_project_todos` and `get_project_archive` both declare `permission: 'projects.read'` with the rest in `additionalPermissions`, and both live in `tools/project-pages.ts`, not in their category's tool file. §54's `requiredPermissions` metadata publishes the singular key unchanged.
- `ProjectPageKindSchema` contains `reflections`; `NAVIGABLE_PAGE_KINDS` lists it last, in §23's column order; `pageAcceptsSectionType` narrows that page to a reflections container through `SECTION_OWNERSHIP`. `PROJECT_PAGE_REGISTRY` has no `reflections` entry, so `resolveProjectPage` answers "not built yet". §26 and §30 both say Reflections owns **one** container, singular.
- Registering this renderer makes all four navigable kinds drawable, so `resolveProjectPage`'s `definition === undefined` branch becomes unreachable — `work` is turned away earlier by `!isNavigablePageKind(kind)`, not by the `!isRootProject` branch, which does not fire for a root routed to `/pages/work`.
- `project-page-navigation.spec.ts` asserts the tab list `['🏠 Home', '🗓️ Todos', '🗄️ Archive']`, and its *"advertises no page kind without a renderer"* test is `navigablePages`' only direct coverage — it uses `reflections` as its undrawable kind and cannot be re-expressed once every navigable kind is drawable. `project-workspace-shell.spec.ts` separately asserts the `'not built yet'` fallback on the same kind.
- `ProjectPageService.setEnabled` creates a page record and no content, so an enabled Reflections page starts with zero sections.
- `reflections-section.html` renders the composer form **and** the container's editable entry list in one template; `reflections-section.ts` declares `providers: [ReflectionsStore]`, so the store is section-scoped and invisible to a page; `ReflectionsStore.create(bodyRaw, titleRaw, prompt)` is positional with no subject slot; `ReflectionsStore` exposes a **single** `error` signal for load, create and edit alike, and `reflections-section.spec.ts` asserts `[data-reflections-error]` for a *load* failure. `reflections-section.scss` owns `.reflections__composer` and `.reflections__error`, which stop applying once that markup moves into a child component.
- `ProjectPageRendererInputs` supplies seven inputs with stable callback identity; `ArchivePageStore` is the model for generations, write epochs, `PendingTasks`, `DestroyRef` teardown and `LIVE_UPDATES` invalidation. `ActivityService` stamps `rootProjectId` on every event carrying a `projectId`, so a descendant write reaches an open root page.
- `apps/prototype-host/main.ts` enumerates every service into `createToolRegistry({ projects, pages, todos, archive, tasks, reflections, sections, shortcuts, dashboard, workspace })`. `registry.test.ts` hard-codes the tool count (`toHaveLength(32)`) beside a prose enumeration.
- `PROTOTYPE_AGENT_TOKENS` maps three fixed tokens — read/write, read-only, revoked — but the **connection behind a token is mutable**: `routes.test.ts` already narrows `agent-claude` with `PATCH /api/agent-connections/agent-claude` and then calls with the read/write token, and `apps/e2e/archive.spec.ts` issues the same persona-headed `/api/*` calls. So any harness with persona API access can mint a write-only grant; only `mcp-acceptance.mjs` cannot, because it makes no `/api/*` calls. `contract.test.ts` mints grants directly (`agent(['reflections.write'])`) and is table-driven, which is why the write-only case belongs there — cost, not impossibility.
- The `agent-heavy` seed **does** hold a completed task: `task-agent-deployment` (`status: 'done'`), on root `project-work-manager`, and `harness.ts` names it in `OPEN_TASK`'s own comment. That root's Home has no reflections container, which is not an obstacle — `resolveContainer` creates one. The seed has **no completed sub-project**, so that subject branch is exercised in domain and store tests rather than over a transport.
- `mcp-acceptance.mjs` copies `agent-heavy.json` to a temp dir and drives **MCP only**: no `/api/*` calls, no browser, and `assertPersisted` re-reads the file after `stopHost` without ever starting a second host.
- `packages/domain` tests build documents with `twoPersonaDocument()` from `packages/domain/test/test-support.ts` and load no seed file. `test-support.ts` constructs `new ReflectionService({...})`.
- `validateDocumentIntegrity` has a cycle-guarded `rootProjectId(projectId)` helper, used for the shortcut same-root rule.
- `SCHEMA_VERSION` is 3. A new optional field is additive: documents written by 25.1–25.6 parse unchanged and no converter is in scope.

## Acceptance check

Parent **Done when**, verbatim:

> complete a task and nested subproject, write one reflection for each, view both alongside existing journals on root Reflections, and reopen a subject without losing history. Create a subject-linked reflection through MCP and observe the live UI update.

Made executable with fixtures built **at the layer that can represent each case**: `twoPersonaDocument()` for ordinary domain/host cases, an inline hand-crafted `PrototypeDocument` for a completed sub-project beneath an archived ancestor (canonical writes refuse creating that state), and per-spec API setup over `agent-heavy` for browser and MCP. The browser spec creates its foreign-workspace control through a local `apiAs('user-alex', ...)` helper, because the existing shared helper always authenticates as `user-demo`. No distributed seed file is edited.

**The journey advances the clock.** Every existing e2e spec pins the simulated clock once and never moves it, so reflections created in one run would all share a `createdAt` and "newest-first" would collapse onto the ordinal id tie-break — an artifact of id text, not a chronology. This journey calls `setClock` between each seeded and written entry, and asserts an explicit expected id order rather than the words "newest first".

1. Build a root with Home, an enabled Reflections page and an enabled Todos page; a child sub-project and a grandchild, each with a work canvas; a reflections container on Home, one on the Reflections page and one on the grandchild canvas; a task list on the child holding **two** tasks. Seed one pre-existing subject-less journal entry **on Home** and one **on the grandchild canvas**, so all three sources have content before anything is written. Create a second root as `user-demo`, and create a foreign-workspace project through the local `apiAs('user-alex', ...)` helper, for exclusion controls.
2. Complete the first task on the child and complete the grandchild sub-project. Both appear in the completed-work picker with their kind, name, completion time and origin breadcrumb. Incomplete work, archived work, work under an archived ancestor, work in the other root and work in the foreign workspace do not appear. The under-archived-ancestor candidate is asserted from the hand-crafted document/host fixture described above; the browser journey covers the reachable cases. Completed work carrying no `completedAt` still appears, ordered last. An empty picker states so.
3. Write one reflection about the completed task and one about the completed sub-project, each through the page composer, which names the container it writes into. Both land in that named container — `sectionId` equal to the one displayed, `projectId` the reflection's own project — and neither the task nor the sub-project changes container, page, position or any field.
4. The Reflections page shows **four** entries newest-first, aggregated from Home, the page's own container and the grandchild canvas, each with its origin breadcrumb and canonical owner link, and for the two linked ones the subject's kind, name and **current** state. The two entries with no subject render as ordinary first-class entries, not as errors or gaps. The composer region renders no second copy of the page container's entries.
5. In order: reopen the task to `todo` and set the sub-project back to `active`; assert both reflections survive, keep their subject, and display the reopened state. Then archive the task; assert its reflection still appears, resolved, with an archived-subject state — the journal resolves subjects with `includeArchived`, which is what makes this observable at all. Compare the stored reflection rows before and after: nothing changed except through an explicit reflection write.
6. Refusals, **as a person** (who holds every message the design allows), each writing no reflection row, no activity row and no live event: the browser/API journey covers a subject in another root of the same workspace, one that is not currently completed, a completed **task** that is archived, and a `subproject` subject naming a root. The completed sub-project beneath an archived ancestor is covered by the hand-crafted `PrototypeDocument` fixture in domain and host-route tests, because canonical project archive writes refuse live descendants. A subject that does not exist and one in another workspace are refused **identically** — `EntityNotFoundError`, 404 — because the repository deliberately does not distinguish them. A reflection written into an archived project or archived section is still refused by the existing rules.
7. Disable the Reflections page, reload its URL, and see the Home fallback with its explanation; the entries are still stored and still visible in their owning containers on Home and the grandchild canvas. Re-enable it and the same entries return unchanged.
8. **Browser and MCP-over-HTTP, in Playwright** (which owns the per-spec API fixture): complete the *second* child task, so an eligible subject exists again after step 5. Then, with the read/write token, `add_reflection` naming it succeeds and the response body carries the subject ids and **no** task title or project name; `get_project_journal` returns the five entries the HTTP route returns, compared against expected ids rather than against each other; the read-only token cannot write; `add_reflection` naming only the Reflections `pageId` on a page with no container creates that container, and the page shows it on the next read (six entries). With the browser open on the Reflections page, the MCP create on the grandchild canvas refreshes the feed without a manual reload.
9. **Two-transport script** (`mcp-acceptance.mjs`, raw `agent-heavy`, MCP only): a subject-linked create naming `task-agent-deployment` — the seed's completed task, whose root has no reflections container, so the create also exercises `resolveContainer` — over Streamable HTTP and over stdio, then a **start-after-stop re-read**. The script currently re-reads the file after `stopHost` without restarting; this slice adds the second `startHost` so persistence is proven by a running host rather than by the file alone. The script makes no `/api/*` calls, so it cannot narrow a connection's grants; the **write-only** path lives in `contract.test.ts` (table-driven and cheapest) and its HTTP status equivalence in `routes.test.ts`, which already narrows `agent-claude` through `PATCH /api/agent-connections/:id`.
10. Deterministic failure injection is covered by the page/store tests: the composer keeps its draft text, shows the host's message, and the feed gains no phantom row; a retry after the failure succeeds and appears exactly once. Separately, a create that commits while the follow-up feed read fails reports the **refresh** as failed, not the write, and offers a read-only retry. The Playwright journey does not claim this second case: the current browser failure control is global/random per request and cannot deterministically fail only the follow-up read without adding a new failure-injection mechanism, which is outside this slice.

## Proposed implementation

### The subject, on the canonical record

Add to `packages/contracts/src/reflection.ts`:

```ts
ReflectionSubjectSchema = discriminatedUnion('kind', [
  { kind: 'task',       id: TaskIdSchema },
  { kind: 'subproject', id: ProjectIdSchema },
])
```

§36's shape verbatim, as a real union rather than a `kind` beside a loose `id`, so a `TaskId` cannot be *written* under `subproject`. That guarantee is **type-level**: `brandedId` is `z.string().min(1).brand(...)` and the brand exists only for the type system, so `ReflectionSubjectSchema.parse({ kind: 'subproject', id: 'task-1' })` succeeds at runtime. The union is asserted the way `ids.test.ts` already asserts branding — a `@ts-expect-error` compile-time case — and the runtime parser tests cover what the union actually enforces: an unknown `kind`, a missing `id`, an empty `id`. Widening `brandedId` to check at runtime is a separate change and out of scope.

`ReflectionSchema.subject` is optional; absent is a general journal entry and stays first-class. Nothing else on the record changes.

**The subject carries ids only.** That is what makes `reflections.write`-alone attachment safe: the stored record, `GET /api/reflections` and `list_reflections` gain two identifiers and no task title or project name, so their permissions are unchanged. Every *resolved* name or status is a separate read with its own grants.

`CreateReflectionInputSchema` gains `subject` (optional). `UpdateReflectionInputSchema` gains `subject` as nullable-optional: absent leaves it alone, a value assigns, `null` clears.

### Domain validation, in `ReflectionService`

Inject `tasks: TaskRepository` — the repository, not `TaskService`, so no new service edge and no `tasks.read` requirement inside a `reflections.write` path.

`assertSubjectEligible(reflection.projectId, subject)` runs inside the existing unit of work, **before `resolveSection`** on create, and on an update **only when the supplied subject differs from the stored one**. Order matters for legibility rather than correctness: `resolveContainer` can create a container and record `project.section_added`, and although a rollback would undo it, `failed create writes no row, no activity and no event` is a much clearer test when an ineligible subject is refused before anything is written at all. Re-supplying an unchanged subject is a no-op, consistent with `update`'s existing equality short-circuit: a client that echoes the whole record must not be refused an unrelated body edit because the subject has since been archived, which is exactly what §36's survival rule forbids. `null` clears without validation, because it references nothing.

Eligibility requires **all** of:

- the subject exists, and its project is in the actor's workspace;
- its root is the same root as the reflection's own project, walked through `parentProjectId` on both sides over the workspace project set;
- for a `subproject` subject, the project is `kind: 'subproject'`. A root is never a subject: §36 names tasks and sub-projects, and a root is the tree, not work inside it;
- it is currently completed: a task with `status === 'done'`, a sub-project with `status === 'completed'`;
- it is visible: for a task, `archivedAt === undefined`; for a sub-project, the `completed` check already excludes `archived`, since `ProjectStatusSchema` is one enum. Both kinds additionally require no archived ancestor.

**The refusal collapses the error, not only the message.** A missing subject is `EntityNotFoundError` (404); the eligibility refusals are `DomainRuleError` (409). Two classes are two status codes, so matching message strings would still let a `reflections.write`-only agent probe any task id — 404 means "no such task", 409 means "it exists but is ineligible". So when the actor does **not** hold the subject category's read grant (`tasks.read` for a task, `projects.read` for a sub-project), every cause — missing, foreign, wrong kind, incomplete, archived — raises the same `DomainRuleError('that subject cannot be reflected on')`. Only an actor holding that grant gets the specific class and message — and even then the message names only what that grant already exposes: `tasks.read` carries `Task.projectId`, so naming the task and its own project is fine, while naming an ancestor or the root is not. `holds(actor, permission)` is added beside `assertPermitted` in `packages/domain/src/actor.ts` and **mirrors it**: `true` for `user` and `system` actors, membership test for an agent — a person holds no grant to check, and returning `false` for them would degrade every message in the browser. §54 says a page is never a permission bypass, and an error channel is a channel.

**Retention is the absence of code, and the tests say so.** No reopen, archive, restore or completion path in `TaskService` or `ProjectService` touches reflections, and none is added: the reflection keeps its subject and the display resolves the subject's current state at read time.

Ownership is untouched: `resolveSection` still decides the container, and a subject never moves, renames or re-parents anything.

`validateDocumentIntegrity` gains a **deliberately narrow** load-time check: a reflection's subject must name an existing task, or an existing project of kind `subproject`. It checks existence and kind, and **not** tree membership, completion or archive state. Tree membership looks like an invariant but is not one: `ProjectService` permits reparenting to any project in the workspace, integrity runs on persist, and a same-root rule here would abort a legal `PATCH /api/projects/:id` with a `DocumentIntegrityError` instead of a domain refusal — the same argument the plan already makes against a load-time completion check. Same-root is an **assignment-time** rule, enforced above; a subject that later leaves the tree is resolved at read time and simply carries no subject view.

### One comparator, all the way to the screen

Extract `instantOf`, `compareText` and `compareInstants` from `project-todos-service.ts` into **new** `packages/domain/src/instants.ts` and import them in both projections. §11's one-definition rule applies to comparison logic two projections must agree on. `project-todos-service.test.ts` references none of the three symbols, so Todos' order suite stays green unedited.

`ReflectionService.list` moves to the same ordinal comparator: `createdAt` descending by instant, then `id` descending ordinally.

`ReflectionsStore` **stops re-sorting**. Its browser-side `localeCompare` with no id tie-break is the order a canvas container actually renders, so leaving it would make "the page and a container agree" false no matter what the domain does — and `apps/web` cannot import `@cwm/domain` to share the comparator anyway. The gateway already returns ordered rows; the store renders them as delivered. This is the whole change: one deleted `.sort(...)`, pinned by a test.

### The two reads

Add `packages/contracts/src/project-journal.ts`. Reuse canonical `ReflectionSchema`, ids and page kinds, and reuse **both** `TodoBreadcrumbStepSchema` and `TodoTaskOriginSchema` from `project-todos.ts` rather than defining third copies — `project-archive.ts` duplicated the step as `ArchiveBreadcrumbStepSchema` and that is the mistake not to repeat. A journal item's origin is `TodoTaskOriginSchema` field for field (`projectId`, `pageId`, `pageKind`, `breadcrumb`, `sectionId`, `sectionName`), so redeclaring it here would be the §11 violation this paragraph is about, one level up from the one it avoids. (`ProjectArchiveOriginSchema` is genuinely different — it adds `pageEnabled` and makes the section fields optional — so it is not the shape to reuse.) The Todos-flavoured names in a journal result are noted here so no reader is surprised by them; renaming them would touch two shipped contracts for no behaviour.

`ReflectionSubjectViewSchema` is **discriminated by `kind`**, matching `ReflectionSubjectSchema` and `ProjectTodoItemSchema`: the two branches carry disjoint status enums (`TaskStatus` vs `ProjectStatus`) and disjoint archive facts, and one flat `status` key over two enums is the guess-which-fields shape §11 forbids. Each branch has `id`, `name`, `completedAt?`, `archived` (task: `archivedAt !== undefined`; sub-project: `status === 'archived'`), `hiddenByArchivedAncestor`, and a root→owner breadcrumb. No routes, for the reason `project-todos.ts` states.

- **`ProjectJournalResult`** = `{ projectId, items: [{ reflection, origin: TodoTaskOrigin, subject?: ReflectionSubjectView }] }`, newest first by the ordinal comparator — §36's aggregation from Home, the Reflections page and descendant canvases, **by reading them, not by moving them**. `sectionName` comes from `nameOf`.
- **`ProjectCompletedWorkResult`** = `{ projectId, candidates: ReflectionSubjectView[] }` — the picker, and only the picker. Currently completed, non-archived, non-hidden work in the tree, ordered by completion time descending with **no completion time last**, then kind (`subproject` before `task`, as Todos orders them), then id ordinally. Candidates reuse the subject view, so `archived` and `hiddenByArchivedAncestor` are always `false` there by construction; they are meaningful only on a journal item's resolved subject.

There is deliberately no "which work has already been reflected on" set in either result: computing one reads the `reflections` collection, and returning it from the picker would disclose reflection activity to an actor holding no reflections grant.

`ProjectJournalService` in `packages/domain/src/project-journal-service.ts` depends on project, page, section, task and reflection **repositories** only — named for the read it serves, as `ProjectTodosService` and `ProjectArchiveService` are, and keyed `journal` beside the existing `reflections: ReflectionService`. Two methods:

- `journal(actor, projectId)` asserts `projects.read`, `tasks.read` and `reflections.read` before any content read. All three unconditionally, even on a fixture where no entry has a subject: §54 requires a derived page to hold the grant for each category it can return and to deny rather than answer partially, and a permission that depended on the data would leak whether linked entries exist.
- `completedWork(actor, projectId)` asserts `projects.read` and `tasks.read`. It returns no reflection-derived data, so it does not require `reflections.read`.

**Two read scopes, deliberately different.** Reflection rows, container/page resolution and the picker read **live only**, as Todos does. *Subject resolution* reads tasks with `includeArchived: true`, because §36 requires an archived subject to keep displaying its state — with the default live-only read the row simply would not be found and the view would resolve to nothing instead of to `archived: true`. This is the one place the slice surfaces an archived entity's name outside Archive, and §36's survival rule is what authorizes it.

Both methods take a **root** id and behave the same way at the edges — `EntityNotFoundError` for missing or foreign, `DomainRuleError` naming the model mistake for a sub-project, empty result for an archived root. Both use `archivedAncestry`, and skip reflections whose container or container's page is missing. Neither is called from a sub-project canvas; nothing in this slice needs a tree-relative entry point.

### Transports

- `GET /api/projects/:id/journal` → `journal`. `GET /api/projects/:id/completed-work` → `completedWork`. `:id` on both, following the two nearest analogues, `/:id/todos` and `/:id/archive`; `:projectId` in this table is served by a differently-named helper.
- `POST /api/reflections` and `PATCH /api/reflections/:id` need no route change beyond the widened input schemas they already parse.
- Gateway: a **new top-level `journal: JournalGateway`** with `get(projectId)` and `completedWork(projectId)`, following the dedicated-seam precedent `TodosGateway` and `ArchiveGateway` set.
- MCP: `get_project_journal` in `tools/project-pages.ts` beside the other two derived-page tools, declaring `permission: 'projects.read'` with `additionalPermissions: ['tasks.read', 'reflections.read']` — byte-identical to `get_project_archive`'s grant set, which keeps `contract.test.ts`'s per-grant denial loop symmetric and keeps `projects.read` in the singular key §54's metadata publishes. `add_reflection`'s schema carries `subject`, and its description says what a subject is, that it must be completed work in the same root, and that attaching one moves nothing. **No** MCP tool for the picker: `shortcut-sources` is the standing precedent for a candidate list that is a route and gateway seam only.

### The Reflections page

Register `{ kind: 'reflections', label: 'Reflections', icon: '📓', component: ReflectionsPage }`, appended after `archive` to match `NAVIGABLE_PAGE_KINDS`' documented column order.

Extract the composer form from `reflections-section.html` into **new** presentational `sections/reflections/reflection-composer.{ts,html,scss,spec.ts,stories.ts}`: title, prompt, body, submit, draft retention, and an optional armed subject shown as a removable chip. Its error line is an **input** its owner supplies, not a store read — `ReflectionsStore` has one `error` signal for load, create and edit alike, so the section keeps `[data-reflections-error]` for load failures (the assertion its existing spec makes) and passes create failures down. `.reflections__composer` moves to the composer's own stylesheet, since emulated encapsulation stops the section's copy from applying. `ReflectionsStore.create` gains a subject argument; `ReflectionsSection` keeps its section-scoped store and passes `undefined`.

`ReflectionsPage` declares all seven `ProjectPageRendererInputs`, provides `ReflectionsPageStore` locally, and renders three regions:

1. **Composer.** `ReflectionComposer` bound to the page's own reflections container and the armed subject. It does **not** embed `ReflectionsSection`, which would render the page container's rows a second time beside the feed. §36 requires the composer to name its container: with one container it shows that name; with none — the state every newly enabled page starts in — it shows an explicit **Add a reflections container** action calling the existing section create with this `pageId`, awaited, with its own failure message, and calling `onProjectHierarchyChange` on success because a new section changes the canvas the column describes; with several, which §26 and §30 do not intend but `create_section` and `resolveContainer` can produce, it writes to the first by position, names it, and says the others are read here too. No selector is built for a state the model does not intend.
2. **Completed-work picker.** Candidates with kind, name, completion time and breadcrumb, filterable by name, with an explicit **no completed work yet** empty state. Choosing one arms the composer; clearing it disarms. An entry with no armed subject is a plain journal entry and submits normally — there is no separate mode to get wrong.
3. **Journal feed.** Every entry newest-first with origin breadcrumb, canonical owner link (project route plus page and section fragment, as 25.5's canonical navigation does), and for a linked entry the subject's kind, name and current state — including reopened and archived — so §36's survival requirement is visible rather than merely stored. A subject that no longer resolves (reparented out of the tree, or deleted from a hand-edited document) is labelled as unavailable rather than dropped. Feed entries are **read-only** in this slice; editing happens in the owning container, reached by the link.

The two reads are independent and their failures are reported separately, the distinction 25.6 asked for: a failed picker read leaves the journal readable and disables only the picker; a failed journal read leaves the composer usable. Both offer retry.

`ReflectionsPageStore` follows `ArchivePageStore`: read generations, a write epoch that discards reads already in flight when a write begins, `PendingTasks`, `DestroyRef` teardown, and a `LIVE_UPDATES` subscription invalidating on this root's `reflection.*`, `task.*` and `project.*` frames — matched on `rootProjectId` — and on reconnect. Results from a superseded generation, a changed root or a destroyed store change no state and call no shell callback. A successful reflection create refreshes the feed and calls `onProjectDataChange`; it does not call `onProjectHierarchyChange`, because a reflection changes no hierarchy. If a create commits and the refresh fails, the store says the **refresh** failed, keeps the draft cleared, and offers a read-only retry — it never reports the write as failed.

**On an ordinary canvas, a linked reflection shows that it is linked and nothing more.** `ReflectionsSection` renders a neutral marker — *"About completed work · see Reflections"* — from the `subject` the row already carries. It resolves no name or status, so it needs no extra read, no `tasks.read`, and no failure branch, and it cannot leak a task title to an actor holding only `reflections.read`. Resolved subject identity is a Reflections-page feature, where all three grants are asserted. This narrows the roadmap's "show subject identity/status" for the section; the reason is recorded in the decision entry, and widening it later is a bounded change once the page has been used.

## Boundaries touched and explicit non-goals

Components → feature store → gateway interface only; HTTP lives in the adapter and host composition. `ProjectJournalService` uses repositories, never transport or JSON adapters, and adds no service edge. `ReflectionService` gains a **repository**, so the acyclic service graph is unchanged and no `TaskService ↔ ReflectionService` cycle appears. Contracts are defined once in `packages/contracts`; the subject union and the subject view have no parallel definitions, the breadcrumb step is reused rather than copied, and the instant comparator is extracted rather than duplicated (both consumers are in `packages/domain`; the web store stops sorting instead of importing it). Writes keep `Clock`, the unit of work, activity attribution and post-commit events. Token-only styles, no global store, no new prototype flag, no migration and no new collection.

Not in this slice: resolved subject names or statuses on ordinary canvases; editing or archiving a reflection from the feed; moving reflections between containers or pages; a container selector on the Reflections page; a root-tree guard on project reparenting; subjects that are sections, reflections, milestones, roots or anything in another root; an MCP picker tool or an MCP reflection-update tool; a write-only seed token; automatic reflection prompts on completion; notifications, digests or streaks; Calendar, Timeline, Milestone or AI expansion; shortcut placements for the journal; the integrated seed, Storybook sweep and documentation closure that belong to 25.8; any change to archive cascade, undo semantics or the Archive page beyond reading its rules.

## Open questions

None blocking planning. Five are deliberate prototype choices to record in `docs/decisions/` and evaluate in use:

- **The feed is read-only.** Editing lives in the owning container, reached by the canonical link. Editing in place would give one reflection two editors.
- **A canvas shows that a reflection is linked, not what it is linked to.** Resolving the name on a canvas needs `tasks.read` the canvas does not require, and a whole-tree read per container.
- **Attach requires currently-completed, visible work; display never re-checks it, and resolves archived subjects on purpose.** Separating "eligible at assignment" from "resolved at read" is what lets an entry survive a reopen, and reading subjects with `includeArchived` is what makes the archived state visible rather than blank. It is the one place this slice names an archived entity outside Archive.
- **Refusal detail follows the actor's grants.** A person sees the specific reason; an agent without the subject category's read grant sees one class, one status and one message for every cause. The cost is a worse error for a legitimately confused write-only agent, and it is worth watching whether that hurts in use.
- **A newly enabled Reflections page has no container and says so** — while an agent write naming that page still creates one through `resolveContainer`. The two are consistent (the page never resolves invisibly; the write path always has), but the asymmetry is worth watching.
