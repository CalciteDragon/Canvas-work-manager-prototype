# Slice 25.4 — Add shortcut to Home

**Status:** draft — not started.
**Roadmap:** [25-multi-page-projects-overhaul.md](25-multi-page-projects-overhaul.md) §25.4.
**Depends on:** 25.3 (done) — `ProjectWorkspaceShell`, `ProjectCanvas`, `ProjectPageStore` keyed on
one page, `ProjectPageService`, `pageId` on every section, `rootProjectId` on `LiveEvent`, and the
empty `sectionShortcuts` collection reserved by 25.1.

## Goal

Let a root's Home show a section that canonically lives somewhere else in the same root tree —
another of its pages, or any subproject at any depth — as a **reference** that renders the source's
live content read-only, with no row copied and no permission widened.

## Spec sections

§11–15 (contracts, persistence, the document, the unit of work), §26 (roots and work units),
§27 (the ownership chain, where a write lands, **Shortcuts on Home**), §29–30 (registry, the
capability table's "plus shortcut placements"), §31 (the frame, and **where archived work is
found** — an archived owner hides its live contents from ordinary reads), §32 (shortcut placements
are layout; Edit Layout Mode owns adding and removing them), §52–55 (grants, the permission-bypass
rule, the tool registry), §62 (live updates), §63 (optimistic UI), §68 (routes), §69 (testing).

## Acceptance check

Executable form of the roadmap's *Done when*. Every numbered item is something to run.

1. `pnpm test`, `pnpm lint`, `pnpm build` and `pnpm storybook:build` green. `pnpm e2e` still green
   with **no edit to `apps/e2e`** — the combined journey is 25.8's.
2. On the `nested-projects` seed, in a browser at `/projects/project-renovation/pages/home`:
   Edit layout → **Add shortcut** → the picker lists sources grouped by location with breadcrumbs.
   Add `section-project-kitchen-tasks` — the Task List on the nested subproject
   `renovation → kitchen` — and Home paints a shortcut frame rendering that list's real row
   (`task-kitchen-appliances`), naming where it came from, with **Open source**.
   *The seed's depth-3 `project-cabinets` deliberately has no sections at all
   (`prototype/seeds/nested-projects.json`; seed content is 25.8's, and editing it is a non-goal
   here), so the depth-3 case is reached by first creating a Task List on it through MCP
   `create_section`.*
3. That shortcut's content is **read-only**: no add-task form, no completion control, no inline
   title edit, no archive control, no detail drawer, and no drag — the read-only Task List renders
   no `cdkDropList` at all, so its rows cannot be dropped into Home's own Task List and two
   placements of one source cannot collide on a drop-list id. **Open source** navigates to the
   owning canvas, where the same rows are fully editable.
4. Editing the source updates the shortcut on Home without a reload (§62): complete
   `task-kitchen-appliances` from `/projects/project-kitchen` in a second tab, and through MCP
   `complete_task`.
5. Source row counts are unchanged: `GET /api/tasks?sectionId=section-project-kitchen-tasks` returns
   the same rows before the shortcut exists and while it exists. *(The after-removal half is step 9's
   — removing the placement here would take away the one items 6–9 act on.)*
6. Availability, all three states, each restored afterwards:
   **archived source section** — archive it from `/projects/project-kitchen` → the placement shows
   an unavailable state rather than content or an error; restore it → content returns (§27).
   **hidden source** — archive `project-kitchen` itself → the placement goes unavailable, because
   §31 says an archived owner hides its live contents from ordinary reads and Home is one;
   reactivate → content returns.
   *(The third asymmetry — a source on a **disabled** page — is step 8's, where the fixture that
   needs it is built, so this list runs top to bottom.)*
7. Home's ordering is **one sequence**: drag a shortcut above a section and below another, reload,
   and the order holds; drag a section past a shortcut, likewise. Collapsing the placement does not
   collapse the source, and vice versa.
8. Cross-page source, in the browser: enable the root's Reflections page through MCP
   `set_project_page_enabled`, add a reflections container to it through MCP `create_section` with
   an explicit `pageId`, then shortcut **that** onto Home. It renders read-only beside the
   subproject Task List. No Reflections *page renderer* is registered by this slice, and the page
   appears in no navigation — enabling the record and registering a renderer are different things.
   Then disable that page again through `set_project_page_enabled`: the placement **keeps
   rendering** (§27: hiding a page hides navigation, not data).
9. Through MCP: `add_section_shortcut`, `list_section_shortcuts`, `remove_section_shortcut` act on
   the same placement the browser made. `list_section_shortcuts` under `projects.read` **alone**
   returns the placement and its source's identity and returns **no task or reflection rows**, and
   `list_tasks` for that source section still refuses without `tasks.read`. Finish with
   `remove_section_shortcut`: the placement goes, the source section stays on its own canvas, and
   the row count from step 5 is unchanged a third time.
10. Storybook renders `ShortcutFrame` (available, source-archived, source-hidden, collapsed,
    read-only Task List) and `ShortcutPicker` (sources grouped, empty, source already placed).
11. Todos and Archive appear in no navigation and no page renderer, and neither does a Reflections
    renderer. The seeds still ship `sectionShortcuts: []`; 25.8 populates them.
12. A `.prototype/data.json` written by 25.1/25.3 — before any shortcut existed — still loads
    unchanged. Nothing in the stored shape changes in this slice: `sectionShortcuts` and
    `SectionShortcutSchema` landed in 25.1, and `SCHEMA_VERSION` stays at 3.

## Design decisions this plan makes

Stated here so implementation does not re-open them.

### One combined ordering per page, held in one place

§27 is explicit: *"Home holds one combined ordering of its own sections and its shortcut
placements — a shortcut sits in the canvas like anything else."* Two independently dense sequences
cannot express that; a section at position 2 and a placement at position 2 have no defined order.

So positions stay dense **per page over both collections**. A new module
`packages/domain/src/page-placements.ts` holds the two operations that need to see both — list a
page's placements in order, and renumber a given order — and `SectionService` and
`SectionShortcutService` both use it. `SectionService` gains one dependency, a
`SectionShortcutRepository`; it gains no service edge, so §12's acyclic graph is untouched.

**Seven paths touch positions, not five.** In `SectionService`: `addWithin` (appends at the combined
end), `move` (the index is into the combined list, which is what the canvas's drop handler computes),
`duplicate` (splices the copy after the original within the combined list), `remove` (renumbers the
survivors) and `restoreSection` (appends at the combined end). In `SectionShortcutService`: `create`
(appends at the combined end) and `remove` (renumbers the survivors), plus `move`, which is the
placement's own reorder over the same list. Tests 13–17 cover `SectionService`'s five and tests
18–20 the shortcut service's three. The intricate ones get their own case rather than riding on an
append: `move` takes a combined index, `duplicate` splices two elements at a `findIndex`, and
`remove` renumbers through what is today a live-**sections**-only read.

On a page with no shortcuts every `SectionService` path behaves as it does today, which is why the
existing `section-service.test.ts` cases stand unchanged — a property worth asserting rather than
assuming, and test 12 does.

*Rejected alternative:* render shortcuts as a band after the sections. It needs no change to
`SectionService` at all, and it is a smaller slice. Rejected because it contradicts §27's sentence
and because "a shortcut sits in the canvas like anything else" is the claim the slice exists to
test — a band answers a different question.

### Resolution returns identity, never rows

§54: *"discovering that a placement exists is `projects.read`, and loading the tasks behind it is
`tasks.read`."* The cheapest way to satisfy that is to make it structural rather than checked:
`SectionShortcutService` never reads a task or a reflection. It has no `TaskRepository` and no
`ReflectionRepository` among its dependencies, so a row leak is unrepresentable rather than
guarded. It answers the placement, the source `ProjectSection` record, the source project and page
identity, the breadcrumb, and an availability state — and nothing else.

The **content** arrives the way it always has: the source section's content component is mounted
with the source's `ProjectSection`, and `TaskListStore`, `ReflectionsStore`, `ProgressStore`,
`TimelineStore` and `ActivityStore` each make their own gateway call, each of which lands on the
domain service that enforces its own grant. Test 23 pins it from both sides.

*Consequence, stated rather than discovered:* MCP has no `resolve_shortcut` returning content. An
agent reads `list_section_shortcuts` for the source ids and then `list_tasks`/`list_reflections`
with its own grants, which is one more call and the correct number of permission checks.

### Availability has three states, and the archived-owner one is not optional

§27 gives one: *"an archived source shows an unavailable placeholder — not its content — and
restoring the source revives the reference."* §31 gives a second that §27 does not mention:
*"A project whose own status is `archived` hides its live contents from ordinary reads too"*, and
Home is an ordinary read. §31's landed note is explicit that *"a read that names a project or a
section always answers"* — so `tasks.list({ sectionId })` will happily return the rows of a section
inside an archived subproject. Nothing downstream stops it. The shortcut layer has to.

```
available      — the source section is live, and its project is neither archived nor beneath an
                 archived ancestor
source_archived — the source section carries archivedAt (§27)
source_hidden   — the source section is live, but its project is archived or has an archived
                 ancestor (§31)
```

`project-visibility.ts`'s `archivedAncestry` already computes both predicates; this reuses it
rather than restating the walk. Two things it is easy to get wrong and this plan states rather than
leaves to be rediscovered: `source_hidden` is `isArchived(p) || hasArchivedAncestor(p)` and
**not** the module's `isHidden`, which deliberately excludes a project archived in its own right;
and the ancestry must be built over the **complete workspace project set before any filter**, which
that module's own comment calls the one way to get it wrong, because it fails silently.
`listSources` excludes both unavailable kinds — offering a source that would immediately render unavailable is not an offer —
and `create` refuses both.

There is deliberately **no `source_missing`**. Sections are never deleted (removal archives, and
`SectionRepository.remove` is unreferenced by `SectionService`), and the integrity rule below makes
a dangling `sourceSectionId` a document that does not load — so no state a running system can reach
would produce it, and a member nothing can produce is a branch no test can cover.

### A placement is not a section, so it gets its own frame

`ProjectSectionFrame` carries §31's affordances for a section the canvas **owns**: rename,
duplicate, configure, remove-with-policy. A placement has none of those — its source is renamed on
its own canvas, and removing it archives nothing. Giving one component both sets of affordances,
switched by a flag, is how the wrong control ends up one boolean from being reachable.

**Add shortcut is a root-Home control, and the canvas cannot tell on its own.** `ProjectCanvas`
renders a root's Home *and* a subproject's work canvas, and it takes only `projectId` and `pageId` —
neither the page kind nor the owner's kind. Left ungated it would offer the control on every work
canvas and open a picker whose every create the domain refuses. `ProjectWorkspaceShell` already
resolves the page kind, so `shortcutsAllowed` becomes a **sixth member of the renderer contract**.

That is three files, not one, and the third is the one easy to miss: the shell mounts renderers
through `NgComponentOutlet`, so the input is added to `rendererInputs`'s computed literal in
`project-workspace-shell.ts` — *not* to its template — **and** to both interfaces in
`project-page-contract.ts`. Adding it only to the literal compiles silently, because
`ProjectPageRendererInputs extends Record<string, unknown>`; it is `ProjectPageRenderer` that makes
"a page registered without one of the shell's inputs fails to compile" true, and 25.5–25.7's
renderers inherit whichever answer this slice leaves. `input.required<boolean>()` on the canvas,
matching its other four. Test 68 asserts the control's absence on a subproject; test 70 asserts the
shell computes the gate, which is the half a component test cannot see.

So `ShortcutFrame` is its own component: **a drag handle** (§32, and acceptance 7), collapse, span,
the source breadcrumb, **Open source**, **Remove shortcut** in Edit Layout Mode, and the two
unavailable states — mounting the source's registered content component through the same
`NgComponentOutlet` contract the section frame uses. `ProjectSectionFrame` changes in exactly one
way: `SectionContentInputs` gains `readOnly`, and the section frame passes `false`.

**All three content callbacks are stable no-ops.** `SectionContentInputs` requires
`onConfigChange`, `onProjectDataChange` and `onProjectHierarchyChange`. Forwarding `onConfigChange`
would write the **source's** config through a view that owns nothing — Rich Text's body saves down
exactly that path — so the shortcut passes a no-op; the other two have nothing to announce, because
a read-only view produces no change. They are class-property arrows for the identity reason
`section-contract.ts` states at length: an inline arrow is a new identity on every change-detection
pass, and in a zoneless app that is a self-feeding loop. Test 55 pins it.

### Read-only is an input the content components honour, not a CSS gate

`pointer-events: none` leaves every control reachable by keyboard and every form submittable.
`readOnly` joins `SectionContentInputs` and `SectionContentComponent`, so a section registered
without it fails to compile; each of the seven components gates its own mutations. Two of them —
Timeline and Recent Activity — have no mutation to gate and declare the input anyway, because the
contract is what the registry types against.

**Task List is the case with the most surface, and the plan names all of it.** Its template binds a
quick-create form, and each `app-task-row` binds `completionRequested`, `titleEdited`,
`archiveRequested` and `selectedRequested`, the last of which opens `app-task-detail-drawer` with
its priority, due-date and estimate writes. Read-only means: no form, no drawer, and `TaskRow`
itself takes a `readOnly` input that hides its completion control, inline title editing and archive
control. The empty-state copy — *"No tasks yet. Add the first one above."* — points at a form that
is not there, so it gets a read-only variant.

And the list renders **no `cdkDropList` at all** when read-only. That is one change closing three
holes: rows cannot be dragged out of a view that owns nothing, `connectedDropIds` becomes moot, and
`taskListDropId(sectionId)` — which is the element's `[id]` — cannot be emitted twice when the same
source is placed twice on one page.

### One store owns the canvas; the second owns the picker

A canvas after this slice is sections **and** placements in one order, and one owner is the only
way the two stay in one order. `ProjectPageStore` already carries everything that ownership needs
and that a second store would have to grow a copy of: the generation-and-page staleness guard, the
quiet-refresh coalescing, `whileWriting`'s deferral of §62 re-reads across an optimistic write, and
the reconcile-after-write path. So it owns both arrays and exposes `placements()`.

This is not §20's mega-store. That rule is about the store every route pays for; `ProjectPageStore`
is provided by `ProjectCanvas` and dies with it, and "one canvas's ordered contents" is exactly its
stated scope. Splitting the list across two stores was measured and rejected on three counts: the
deferral does not compose, so a `project.shortcut_moved` frame — recorded against the destination
project, therefore matching `aboutThisProject` — would fire `refreshSections()` mid-drag in exactly
the window the counter exists to close; a section move renumbers placements too, so each store
would have to re-read on the other's write; and `project-page-store.ts`'s own comment rejects
store-to-store coupling for `ProjectWorkspaceStore`.

`shortcuts/shortcut-store.ts` therefore owns the **picker** only: the `listSources` read for one
destination page, its loading and error state. The picker's **Add shortcut** calls
`ProjectPageStore.addShortcut(...)`, the same way Quick Add calls `addSection`. The roadmap's file
name is kept with that narrowed responsibility, said out loud so a reader does not expect placements
in it.

`sections()` **stays** alongside the new `placements()`. Three callers read a sections-only array
and must keep doing so: `TaskListSection.connectedDropIds`, and `ProjectPageStore`'s own
`reassignTargets` and `removalPromptFor`, which offer a container to hand rows to — a placement is
not one.

**Two reads now, and one of them may fail alone.** `sections.list` governs `loaded`, exactly as
today, because it is what every write's guard is about. A failed `shortcuts.list` sets
`sectionError` and leaves `placements()` at the sections it did get — the idiom `refreshSections`
already states, that the page on screen beats an error the user did not cause — rather than
blanking a canvas that loaded fine. Test 44 covers both directions: the reverse — sections fail,
shortcuts succeed — keeps today's loud error and paints nothing.

`moveSection`'s optimistic preview and its rollback both operate on the **combined** array — the
`from === position` short-circuit, the splice and the failure restore are meaningless over a
sections-only array once the index is a combined one. Test 51 covers the rejected case.

### The picker asks the domain once

Composing the candidate list in the browser would mean one `sections.list` per page per project in
the root tree, plus the breadcrumbs. `SectionShortcutService.listSources` answers it in one read
under `projects.read`: every available section in the root tree that is not on the destination page,
with its project, page kind, breadcrumb and canonical name, plus whether the destination already
places it. One place enforces "same root tree" for both the picker and the create, which is the
point — and the picker is the read that returns the most identity, so test 25 pins its scoping as
hard as the create's.

### Removing a placement deletes it

Every other removal in this prototype archives, because it takes content down with it. A placement
has no content — §27: *"removing a placement never archives the source"* — so there is nothing to
undo and nothing an Archive page could offer. `SectionShortcutRepository.remove` deletes the row.
It is safe where `SectionRepository.remove` is not: no activity event names a shortcut (they name
the destination project, as section events do), so `validateDocumentIntegrity` has no dangling
reference to fail on. `json-repositories.ts`'s comment on the protected `delete` — "Only sections
expose this" — stops being true and is corrected in the same change.

### The rules, and where each is enforced

| Rule | Service | `validateDocumentIntegrity` |
|---|---|---|
| Destination page is a **root's `home`** | create | yes |
| Destination page is enabled | create only (§27: placement, not reading) | no — a page can be disabled afterwards |
| Source and destination in the same **root tree** and workspace | create | yes |
| `sourceSectionId` resolves to a real section — so a **shortcut id is a not-found** | create | yes (source must exist) |
| No shortcut to a section **on the destination page** ("no shortcut to itself") | create | yes |
| Source is live, and its project is neither archived nor hidden | create | no — a source archived later keeps its placement |
| Destination root not archived, and no archived ancestor | create/move/update, via `assertProjectWritable` | no |

**"No shortcut to a shortcut" is a resolution rule, not a type-system one.** `ids.ts` builds every
id as `z.string().min(1).brand(...)`, and its own comment says the brand exists for the type
system — at runtime `SectionIdSchema.parse('shortcut-1')` succeeds. So a caller over HTTP or MCP can
pass a placement id, and what refuses it is that the section lookup finds nothing. Test 11 names it.

Two deliberate asymmetries. A **disabled** source page is a valid source and a valid create — §27
says hiding a page hides navigation, not data — while a disabled *destination* is refused, exactly
as `SectionService.assertPageTakes` refuses a section there. And removal is exempt from the archive
freeze for the reason `SectionService.remove` is: the freeze stops work coming *back* into a project
someone put away, not someone tidying one.

Two placements of the same source on one page are **allowed**. The spec does not forbid it, and
inventing a rule here would be a rule with no requirement behind it; the picker marks an
already-placed source instead. The one mechanical hazard it used to carry — two Task Lists emitting
one drop-list id — is gone, because a read-only list renders no drop list. Test 66 asserts the
duplicate case renders cleanly.

### Live updates: Home follows its root tree

`LiveEvent.rootProjectId` already carries "the root of the tree this change sits in" on every frame
with a project, and `ProjectWorkspaceStore` already routes on it. Shortcuts live only on a **root's**
Home, so the open project *is* the root and `event.rootProjectId === requestedProjectId` is exactly
"somewhere in my tree" — a superset of the source projects, with nothing to keep current.

The alternative — tracking the set of source project ids the resolved placements name — was
rejected: a frame arriving before the placement list has loaded names a project not yet in the set
and is silently dropped, which makes acceptance 4 flaky on first paint.

So, in `ProjectPageStore`, **and only while the page holds at least one placement** (otherwise a
sibling subproject's every write would put a re-read behind Home for nothing):

- a frame whose `rootProjectId` is this project bumps `projectDataRevision`, so the mounted
  read-only content re-reads (acceptance 4);
- a `project.*` frame whose `rootProjectId` is this project also re-reads the **placement list**,
  because a source rename, archive or project archive changes what the placement renders
  (acceptance 6);
- and the **section** list's re-read stays keyed on `event.projectId === projectId`, unwidened.
  Routing sibling subprojects' `project.*` frames into `refreshSections()` would issue a
  `sections.list` for a canvas whose own sections cannot have changed. Three rules, three keys —
  the same separation `ProjectWorkspaceStore` had to make;
- shortcut writes record `project.shortcut_added` / `project.shortcut_moved` /
  `project.shortcut_removed` against the **destination project**, for the reason
  `SectionService.record` names the project: `ActivityEntityType` has no `section_shortcut` member,
  and adding one would pin every placement alive forever through the activity integrity check.

The frame `type` is an open `ActivityActionSchema` regex (`entity.verb`), so no contract enum
changes. Test 47 covers the destination side — a `project.shortcut_added` from a second tab paints
a placement without a reload, which a revision bump alone would not do.

## Boundaries touched

- **Components depend on gateway interfaces.** `ProjectPageStore` and `ShortcutStore` inject
  `WORK_MANAGER_GATEWAY`; `ShortcutFrame` and `ShortcutPicker` inject stores, never a gateway and
  never HTTP.
- **Domain depends on repositories, `Clock` and an acyclic service graph.** `SectionShortcutService`
  takes repositories plus `ActivityService`, which every writer takes; it calls no other domain
  service. `SectionService` gains a *repository*, not a service. `page-placements.ts` is pure over
  repository interfaces, as `project-visibility.ts` is — it imports `@cwm/contracts` and
  `@cwm/repositories` interfaces and nothing else. `import-lint.test.ts` is a denylist rather than
  an allowlist (node builtins, concrete `Json*` repositories, `DataStore`, relative escapes), and
  both new files stay clear of it; both take `Clock`, which is what `time-lint.test.ts` checks.
- **Source identity needs no audit beyond the one store.** The roadmap asks that no destination
  project id reach a source context; every content component already syncs on
  `this.section().projectId`, so handing the frame the **source's** `ProjectSection` is the whole
  mechanism. `ProgressStore` is the single exception, because it is the single canvas-provided
  section store — and it is the one thing this slice moves.
- **MCP calls domain services, never repositories.** `tools/shortcuts.ts` reaches
  `services.shortcuts` only.
- **Contracts defined once.** The resolved shape, the source shape and the five inputs live in
  `packages/contracts` and are used by the host, the gateway, the MCP schemas and the tests.
- **A page is never a permission bypass** (§54). Enforced by shape: the shortcut service holds no
  task or reflection repository, so no code path could return a row.
- **No mega-store.** `ProjectPageStore` grows a second collection of the canvas it already owns and
  stays provided by `ProjectCanvas`; `ShellStore` and `ProjectWorkspaceStore` are untouched.
- **No literal colors, spacing or radii** in `shortcut-frame.scss` / `shortcut-picker.scss`.
- **Persist at existing unit-of-work boundaries**, publish after commit through the existing hub.
  No queue, no new store, no synchronization framework.

## Explicit non-goals

From the roadmap's *Do not* list and this plan's own deferrals:

- **Editable embedded sources.** Read-only with **Open source**; §27 says whether in-place editing
  earns its ambiguity is a question for later use (§83).
- **Cross-root shortcuts**, shortcuts to shortcuts, and shortcuts on any page but Home.
- **Todos, Archive and Reflections page renderers** — 25.5, 25.6, 25.7. No renderer is registered
  here, and nothing new appears in navigation. Acceptance 8 enables a page *record*, which is a
  different thing.
- **Seed content.** Seeds keep `sectionShortcuts: []`; 25.8 populates `nested-projects.json`.
- **`apps/e2e`.** The combined journey and its permission/live paths are 25.8's.
- **Undo for a removed placement.** It deletes; there is no content to restore.
- **A `resolve_shortcut` MCP tool** returning source rows — rejected above.
- **Duplicating a placement**, and per-placement titles. A placement shows the source's canonical
  name, which is what "identifies where it came from" asks for.

## Open questions

None blocking; both defaults are defensible and both are recorded rather than escalated.

1. **Does a placement need its own collapse default?** It stores `collapsed`, and a new placement
   starts expanded like a new section. If running it shows that a shortcut is usually reference
   material, the default may want to flip — a §79 note, not a code change here.
2. **Should the picker offer the destination root's other pages before its subprojects?** The plan
   groups by location, pages before subprojects, depth-first. Cheap to reorder once acceptance 2 has
   been run for real.
