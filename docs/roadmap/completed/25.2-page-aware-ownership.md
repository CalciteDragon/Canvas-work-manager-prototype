## Outcome

**25.2, done.** The page is now the unit of section ownership everywhere a write or a read can
reach it. `ProjectPageService` lists a project's pages and toggles a root's optional three;
`SectionService` resolves §27's three write cases — nothing supplied, a page supplied, a section
supplied — and refuses rather than falling back when a page does not hold that kind of section.
Positions are dense **per page**, so reordering Home never renumbers Reflections, and the one
project-wide read groups by page because two pages both number from zero.

Four product questions were answered rather than assumed, each with a decision entry. An
optional page's record is created by its **first enable**, which is the only reading under which
a document written by 25.1 still loads — and enabling one is the single write the archive freeze
does not cover, because §31 says undo must never be behind a toggle. A disabled page refuses
**placement** and keeps everything already on it, which is how §27's two sentences about disabled
pages stop contradicting each other. And reassigning a container's rows may cross pages within a
project, because §31 constrains the type and not the page.

The shared archived-ancestor rule landed here so Archive can ship before Todos, and closing it
turned out to need both ends. Hiding live work beneath an archived ancestor without also refusing
the two operations that produce it — reparenting under an archived project, reactivating beneath
one — would have manufactured a project that is live, invisible to every list and refused by
every write. The reactivation check is a *transition*, not a state, or it would refuse the rename
that is part of the way out.

Two things the phase found by **using** it rather than by testing it, which is the argument for
§77's step. Enabling the Reflections page and putting a container on it drew that container on
*Home*, because the canvas read was project-wide while a canvas is a page — every domain test
asserted the page filter directly, so none of them looked at what a caller passing nothing got.
`SectionService.list` now answers one page and the root Archive projection follows the same
page-aware ownership rules. And the
archived-ancestor memoisation shared one walk's answer along its path, which is sound on a tree
and wrong on a cycle, where the answer is relative to where the walk began; it made the ancestry
disagree with itself depending on call order, and with the write freeze. Each query now walks its
own chain.

Three more the phase found rather than planned, all caught in plan review across five rounds
and worth recording because each would have been a silently wrong answer rather than a failure.
`SectionService.list`'s archived branch is a direct repository read that never passes through
`ordered`, so page-scoping the sort alone would have answered a page query with the whole
project. `resolveContainer` searching one page while `addWithin` created on another are two
independent resolutions of exactly the thing this slice makes ambiguous. And `TaskService.update`'s
subtask branch re-derives `sectionId` from the parent on *every* update of a task that has one, so
a disabled-page refusal placed on the branch would have refused renaming a subtask.

`LiveEvent` gained `rootProjectId`, resolved by walking the parent chain inside
`ActivityService.record` — a departure from that method reading nothing, stated in its own comment
rather than left as a surprise. A root's Todos and Archive project rows from anywhere beneath it,
so `projectId` alone cannot say which root a deep change concerns. Nothing routes on it yet; 25.3
does.

No navigation changed, and no component changed: the two new gateway methods are exercised by the
gateway spec and the fake. Verified in the browser on a converted `.prototype/data.json`, and over
HTTP and MCP for the create-a-root, nest-a-unit-of-work, enable-a-page journey and its refusals.

### Design decisions this plan makes

#### Pages

**Optional pages are created on first enable, not at project creation.** A root created by 25.1
has one page record, and acceptance check 2 says such a document must still load. Pre-creating
four records would either require an integrity rule those documents fail, or leave the rule
unstated and the records unreachable for existing roots. So `ProjectPageService.setEnabled`
**upserts**: the first `enabled: true` for a kind inserts the record, every later call flips
`enabled` on the record that exists. §26's "defaulting to Home only for a new root" is then the
literal stored state rather than a display convention, and "toggle is nondestructive" is
structural — disabling only writes `enabled: false`, and the page keeps its sections, their
positions and every reference to it.

`validateDocumentIntegrity` needs no change to allow this: its page rules are *counting* rules —
at most one page of each kind per project, exactly one canonical page, canonical pages never
disabled (`data-store.ts:165–194`). Nothing requires an optional page to exist.

**A page is never removed.** `ProjectPageRepository` has no `remove` (25.1 states why), and the
canonical page cannot be disabled. "Cannot remove a required page" is therefore tested as a
refusal from `setEnabled`, which is the only operation that could express it.

**`setEnabled` is allowed on an archived project**, unlike every other write in this codebase.
§31 is explicit: *"Because undo must never be behind a toggle, disabling the Archive page leaves
**Open archive** in the project controls, which enables and opens it."* If the toggle carried
`assertProjectWritable`, the archive of an archived root would be unreachable — the exact
outcome §31 legislates against. It is the same exemption `SectionService.remove` already carries
and for the same reason: the freeze stops work coming *back into* a project someone has put
away, and a toggle moves no work. Recorded as a decision entry.

**The Reflections page's narrower capability is derived, not listed.** §30 says a page kind
declares a capability and is not a hand-maintained list of section names. `pageAcceptsSections`
answers *whether a page holds sections at all*, which is what storage needed in 25.1; this slice
adds `pageAcceptsSectionType(pageKind, type)` beside it in `project-page.ts`:

- `home`, `work` — every registered type.
- `reflections` — only a container that owns `reflections`, read out of `SECTION_OWNERSHIP`
  through the existing `ownedKindOf`. §30's "journal feed" is not a section: 25.7 renders it as
  part of the page.
- `todos`, `archive` — nothing, as today.

Enforced in `SectionService` **and** in `validateDocumentIntegrity`, for the same reason the
coarse rule is: a hand-edited `data.json` must fail at load, not at whichever request first
renders it. It is unreachable on an existing document — every section 25.1 can produce sits on a
`home` or `work` page — so acceptance check 2 holds.

**A missing or foreign page is *not found*, not a rule error.** `resolvePage` today raises
`DomainRuleError` for a page belonging to another project (`section-service.ts:220–222`), which
the host maps to 409 — and a 409 confirms the id exists, which is exactly what
`SectionService.require` and `ProjectService.require` refuse to do for a foreign section or
project. It becomes `EntityNotFoundError('projectPage', pageId)`. The page's *capability*
refusals (does not hold sections, does not hold this type, is disabled) stay `DomainRuleError`:
the caller may see that page, it just may not put that there. This changes an existing
assertion — `section-service.test.ts:613–620` asserts `DomainRuleError` for another project's
page — which is an intended-behaviour change, so the test moves with the code (AGENTS.md §2.4).

**`SectionQuery.pageId` is resolved, not merely filtered.** A stale or foreign `pageId` on the
section list must answer 404 rather than an empty array, the same way `TaskService.list` resolves
`parentTaskId` before filtering (`task-service.ts:95`). `SectionService.list` checks the page
belongs to the named project and raises `EntityNotFoundError` otherwise; the repository predicate
is what applies it afterwards.

#### Sections and pages

**Section positions are dense per page, not per project.** Reordering one page must not renumber
another (§27). There are seven `this.ordered(...)` call sites in `section-service.ts`
(137, 172, 245, 311, 334, 406, 439) and they do **not** all mean the same thing, so this splits
into two reads rather than one parameterised one:

- `orderedOnPage(pageId)` — **required** argument, used by every path that renumbers or places:
  `addWithin` (172), `resolveContainer` (245), `move` (311), `duplicate` (334), `remove` (406),
  `restoreSection` (439). A required argument is the point: nothing checks position density at
  load (`data-store.ts` has no position rule), so a forgotten argument would corrupt an ordering
  with nothing to catch it.
- `ordered(projectId)` — stays project-wide, and keeps exactly one caller: `SectionService.list`
  (137), and only on the branch that names no page.

`ordered(projectId)` additionally gains a tie-break. `byPosition` (`section-service.ts:77`) has
none, and once Home and Reflections each number from 0, a project-wide read interleaves two pages
at equal positions in whatever order the repository returned them. It sorts by page, then
position, then id — grouped and deterministic — which is a consequence of per-page density worth
stating rather than discovering in 25.3, when the canvas moves to a per-page read and the
project-wide one loses its last caller.

`SectionService.list` therefore branches on `pageId` **first** and `includeArchived` second, four
combinations rather than two. With a `pageId`, both branches go through `orderedOnPage`/the
page-filtered repository read. Without one, both use the page → position → id comparator above —
**shared, not just applied inside `ordered`**: `ordered` is live-only
(`section-service.ts:601–602`), so the archived branch has its own inline comparator
(`:138–140`) and would otherwise keep interleaving two pages at equal positions, which is the
defect the tie-break exists to close. Its archived branch (`section-service.ts:138–140`) is a direct
repository read that never goes through `ordered` at all, so without this it would resolve a
`pageId`, refuse a foreign one, and then answer with every section in the project — a silent
wrong answer where the live branch would have been merely unfiltered. Both branches pass
`pageId` down to the repository predicate.

`resolveContainer` moving to `orderedOnPage` is not incidental: it is where default write
resolution happens, and left project-wide a default write would land on whichever page happened
to hold the lowest-positioned matching container. It resolves the page **once** and passes that
`pageId` into `addWithin` when it has to create the container — `{ type: containerTypeFor(owned),
pageId }` — so the page searched and the page written to cannot be resolved independently. That
also keeps the read cost honest: one `resolvePage` (a `projects.find` plus a `pages.list`) plus
one section list, instead of `addWithin` resolving the canonical page a second time.

`resolvePage` gains the section `type` alongside the `pageId` so it can apply
`pageAcceptsSectionType`. On the canonical branch the check is inert — a `home` or `work` page
accepts every type — and it is written that way deliberately rather than threaded conditionally:
one function answers "which page, and may this go there".

This needs no data cutover: every project 25.1 can produce has exactly one section-bearing page,
so its existing dense project-wide sequence is already a dense per-page sequence.

**Default write resolution follows §27's three cases exactly**, in `SectionService`:

- nothing supplied → the project's canonical page, then its first live container of the kind on
  that page, then a new one added there through the ordinary `addWithin`.
- a page supplied → resolve *there* only, and refuse if that page does not accept that kind of
  data. No fallback to somewhere the caller did not name.
- a section supplied → authoritative, and it must agree with any page also supplied. A mismatch
  is an error, not a preference order. This includes the *inherited* case: `TaskService`
  resolves a subtask's container from its parent and returns early without loading the section
  (`task-service.ts:438–457`), so that branch gains one `sections.requireWithin` lookup — the
  unchecked door, so a `tasks.write`-only actor is unaffected — to compare the parent's page
  against a supplied `pageId`.

`CreateTaskInput` and `CreateReflectionInput` gain an optional `pageId` for the middle case.
Resolution stays reachable with `tasks.write` or `reflections.write` alone: it runs through
`resolveContainer`/`requireContainer`, which are already the unchecked doors a row write uses on
its own behalf, and this slice adds no `projects.read` to that path.

**No write places content on a disabled page; everything already there keeps working.** §27 says
flatly *"A write never lands on a disabled page. Silent placement somewhere invisible is worse
than a refusal."* §27's shortcut bullet — *"a source on a disabled page is still a valid source;
hiding a page hides navigation, not data"* — is about **reading** a source, not writing to one.
So the line is drawn at placement, not at the caller's choice of identifier:

Every write path in the three services is classified, so nothing is left to the implementer's
judgement:

- **Refused** when the destination page is disabled: `SectionService.add` and `duplicate` (both
  create a section there); a row create naming a `pageId` or a `sectionId` on it;
  `TaskService.update` moving a `sectionId` onto it (`task-service.ts:185`); `settleRows`'
  `reassign` target on it. Plus the two **subtask** paths that name neither a page nor a
  section and would otherwise slip through both bullets: `TaskService.resolveSection`'s
  `parentTaskId` branch (`task-service.ts:438–445`), which inherits `parent.sectionId` and
  returns before `requireContainer`, and `TaskService.update`'s subtask branch
  (`task-service.ts:187–196`), which sets `next.sectionId = parent.sectionId` on the branch the
  `requireContainer` call does not cover. That branch runs on **every** update of a task that has
  a parent, not only when the parent changes, so the refusal fires only when the resulting
  `sectionId` differs from `current.sectionId` — otherwise renaming a subtask that already lives
  on a disabled page would be refused, which is the Allowed side of this very rule. Both paths
  already need the `requireWithin` lookup this plan adds for the page-agreement check, so the
  refusal needs one `pages.find` on top of the `requireWithin` lookup this plan already adds for
  the page-agreement check: a `ProjectSection` carries `pageId` but not `enabled`, so the section
  record alone cannot answer it.
- **Allowed**: every read; `update`, `move` within the page, `remove` — including
  `policy: 'cascade'`, which names no target — and `restoreSection`, on a section already there;
  rows already there being edited, completed, archived and restored; `TaskService.moveSubtree`,
  which follows a root that has already been checked.

There is deliberately no reflection counterpart to the `sectionId` move: `UpdateReflectionInput`
carries only `title` and `body`, so a reflection cannot change container.

The one extra read this costs is a `pages.find` inside `requireContainer` — it has
`section.pageId` but not the page record — on a row create that names its section, and on a
section move. `resolvePage` already loads the page on every other refused path.

`restoreSection` is deliberately on the allowed side — it returns a section to where it already
lived, which is undo, and §31 requires undo not to sit behind a toggle. Recorded as a decision
entry, because §27's one-sentence rule needs this precision to be implementable.

**Reassign may cross pages within a project, subject to the rule above.** 25.1 deferred "page
agreement on reassign" to this slice, since only now can a project have two section-bearing
pages. §31 says a `reassign` moves rows "to another container of the same type" and states no
page constraint, and both containers render what they hold, so `settleRows` keeps its existing
project + type + liveness checks and adds only the disabled-page refusal. A decision entry
records the absence of a page-equality rule, so it is a decision rather than an oversight, and a
test pins it.

#### Archived ancestors

**One shared module, `packages/domain/src/project-visibility.ts`, not four copies.** It exports
pure helpers over a `Project[]` plus one assertion over a `ProjectRepository`:

- `archivedAncestry(projects)` → `{ isArchived(id), hasArchivedAncestor(id), isHidden(id) }`,
  with a visited set so a cyclic hand-edited document starves nothing.
- `assertProjectWritable(projects, projectId)` → the ancestor-walking replacement for the three
  identical private `assertProjectActive` copies in `TaskService`, `ReflectionService` and
  `SectionService`, with the same visited set.

A repository interface is not a new service edge, so the acyclic domain graph is untouched.

**`archivedAncestry` is built over the complete workspace project set, before any query or
status filter.** This is the module's one real trap and it fails silently in both directions:
handed `DashboardService`'s already-`status !== 'archived'`-filtered array
(`dashboard-service.ts:75–77`) or `WorkspaceService.visibleProjects`'
(`workspace-service.ts:141–145`), the archived ancestors are no longer *in* the array, so
`hasArchivedAncestor` is false for everything and the new filter quietly does nothing; handed
`ProjectService.list`'s caller-supplied `ProjectQuery` result (`project-service.ts:69–72`), a
`parentProjectId` or `status` filter removes ancestors the same way. Every caller therefore reads
`projects.list({ workspaceId })` once for the ancestry and applies its own filters afterwards.

**`isHidden` is precisely `hasArchivedAncestor(id) && !isArchived(id)`** — a project that is
*live* underneath something archived, and nothing else. That precision matters for the callers:
a project archived in its own right is still returned everywhere it is today, so viewing an
archived project's Sub-Projects section still lists its (archived) descendants, and
`status: ['archived']` queries are unchanged. Only the trap state disappears from ordinary
reads.

**How much this filter actually changes, stated honestly.** `assertNoActiveChildren` refuses
archiving a project that has non-archived **direct children**, and it runs on both `archive()`
and `update()` (`project-service.ts:184, 220–230`). Note what that is and is not: it is a
direct-children check, so "an ordinary archive leaves every descendant archived in its own right"
holds **inductively over a document every one of whose archives went through this guard** — not
structurally. A seed, the 25.1 converter's output, or a hand-edited `data.json` (§14) may already
contain a live grandchild under an archived child, and archiving the root of *that* produces the
hidden state directly. Walking the whole subtree in `assertNoActiveChildren` is not in this
slice's scope, so the plan states the limit rather than claiming a guarantee.

On a clean document, `isHidden` fires only on states reached afterwards: reparenting a live
sub-project under an archived one, and reactivating a sub-project whose ancestor is archived.
Both are reachable today. This slice closes them at the write side as well as hiding them at the
read side — otherwise the read filter alone would manufacture a project that is live, invisible
to every list, and refused by every write.

- `ProjectService.create` already refuses a *directly* archived parent; it now refuses an
  archived ancestor.
- `ProjectService.update` refuses reparenting under an archived ancestor, **and** refuses the
  *transition* `current.status === 'archived' && next.status !== 'archived'` while an ancestor is
  archived, naming the ancestor to reactivate first. A transition, not a state: a project that is
  already live under an archived ancestor has `next.status !== 'archived'` on every update, so a
  state predicate would refuse the rename the escape hatch below promises. Reactivating stays an explicit status choice (§31); this only constrains the
  order. The check reads `next.parentProjectId`, **after** the reparent has been applied, so
  `update(P, { status: 'active', parentProjectId: liveParent })` — reactivating and moving out in
  one call, the natural use of the hatch below — succeeds rather than being refused against the
  old parent. Recorded as a decision entry.
- **The escape hatch stays open, and is stated so no implementer closes it.** `assertProjectWritable`
  is applied to *content* writes — sections, tasks, reflections — never to `ProjectService.update`
  as a whole. Renaming a hidden project, and reparenting it away to a live parent, both still
  work; `assertParentIsUsable` already permits the destination. `ProjectService.get` also keeps
  answering for a hidden project, so an id already in hand still reaches it — which is what makes
  the hatch usable for a document that arrived with hidden projects already in it. That is the
  only read path to one between this slice and 25.6's Archive page; the write refusals stop new
  ones being created, they do not retro-fit a browser for existing ones.

**Which reads change, precisely.** "Ordinary content reads" is not "every read":

| Read | Change |
|---|---|
| `DashboardService.load` | keeps its `status !== 'archived'` filter (`dashboard-service.ts:75–77`) and also drops `isHidden` projects. The two are complementary, not alternatives: `isHidden` is deliberately false for a project archived in its own right. |
| `WorkspaceService.search` / `upcomingWork` | same, over `visibleProjects` (`workspace-service.ts:141–145`) |
| `TimelineService.derive` | **unchanged.** Its `descendants` walk is root-relative — it starts at the project the caller named whatever that project's status is, and prunes archived children with their subtrees (`timeline-service.ts:66–77`). Replacing that with the global predicate would change the answer for a timeline requested *on* an archived project, which §31 says must still render. The roadmap names this file; the finding is that its declared scope already satisfies the rule, so it is pinned with tests rather than rewritten. |
| `ProgressService.calculate` | **unchanged** — it measures the direct tasks of a project the caller named by id, and 25.2 requires each read model's declared scope preserved. Pinned with a test. |
| `TaskService.list` naming **no project, no section and no parent task** | excludes `isArchived(id) \|\| isHidden(id)` — **both**, unlike every other row in this table. It is the one caller with no archived filter of its own (`task-service.ts:96–99` builds `visible` from every workspace project), so `isHidden` alone would leave §31's "a project whose own status is archived hides its live contents from ordinary reads too" unmet and a truly unscoped `list_tasks` still leaking archived projects' work. The discriminator is deliberately all three, not `projectId` alone: the canvas's Task List reads `{ sectionId }` with no project (`task-list-store.ts:94, 143`), so keying on `projectId` would blank every Task List on an archived project's own page — the thing the next row says §31 forbids. |
| `TaskService.list` naming any of them, `SectionService.list`, `ReflectionService.list` | unchanged: the caller named where to look, and §31 requires an archived project's own page and Archived region to keep rendering |
| `ProjectService.list` | drops `isHidden` projects. `shell-store.ts` and `state-inspector-store.ts` already filter archived out; `sub-projects-store.ts` and `list_projects` are unfiltered and see no change, because every descendant of an archived project is archived itself. `assertNoActiveChildren` reads the repository, not this method, so the archive guard is untouched. |

No new `ProjectQuery` member: 25.6's Archive page reads the tree through its own service, and a
query field with no caller in this slice would be published to agents through `list_projects`'s
JSON Schema with no behaviour behind it.

#### Live updates

**Live invalidation names the root.** `LiveEvent` gains an optional `rootProjectId`, resolved in
`ActivityService.record` by walking `parentProjectId` through the project repository it already
holds — with a visited set, for the reason `ProjectService.assertParentIsUsable` carries one
(`project-service.ts:236–241`): a hand-edited document can contain a cycle, and `record` runs
inside every mutation. A change deep in a tree must invalidate the root's aggregate pages
(Todos, Archive), and `projectId` alone cannot say which root that is. `record`'s "uses none of
them" comment about the read repositories is corrected in the same change. The hub buffers the
whole `LivePublication` and flushes after commit (`hub.ts:67–78`), so the extra field rides
along and a rolled-back unit still announces nothing. Routing on the field is 25.3's; this slice
publishes it and tests that it arrives.

#### Domain (`packages/domain/src`)

- **new** `project-page-service.ts` — `list(actor, projectId)` under `projects.read`, asserting

### Boundaries touched

### Revisions

**Round 1** returned fourteen findings. The ones that changed the shape of the work: the
foreign-page error class had to move to `EntityNotFoundError` or acceptance check 5 could not
pass; the read filter without matching write refusals would have created a live-but-unreachable
project, so reactivation is now refused too; `TimelineService` was going to be "restated through
the shared helper", which would have silently changed its root-relative scope, so it is left
alone and pinned; a proposed `ProjectQuery.includeArchivedDescendants` had no caller and would
have been published to agents through `list_projects`, so it is deferred to 25.6 with its
consumer; the root walk in `ActivityService.record` needed the cycle guard `ProjectService`
already carries; and the acceptance check cited `import-lint.test.ts`, which only tests the
scanner against temp directories. Two items 25.1 handed forward — reassign's page rule and
richer project tool descriptions — were missing entirely.

**Round 2** returned sixteen more, five of them substantive. `ordered` was described as one
parameterised read when it is two with different meanings, and the missed call site was
`resolveContainer` — default write resolution itself, which would have picked a container off
the wrong page; the fix is a required-argument `orderedOnPage` plus a project-wide `ordered` with
one caller. `setEnabled` on an archived project was unspecified, and §31's "undo must never be
behind a toggle" settles it as the one write the archive freeze does not cover. The round-1
"named page refused, named section allowed" split was not self-consistent — `duplicate`,
`reassign` and a `sectionId` move all place content with no page check — so the rule is restated
around *placement versus editing*, which is both implementable and closer to §27. The claim that
`ProjectService.list`'s filter left `sub-projects-store.ts` unaffected was under-specified rather
than wrong: the predicate is `hasArchivedAncestor && !isArchived`, so archived descendants are
still returned and the section still renders; the plan now says the predicate rather than the
prose. And `failed write emits no live event` already exists and already passes, so it is
labelled as re-run coverage and a genuinely new rollback test — a failed page enable — takes its
place on the list. The rest were checklist repairs: the existing `section-service.test.ts`
assertion that moves with the error class, `registry.test.ts`'s hardcoded tool count,
`SPEC_TOOL_NAMES` being order-asserted by `handler.test.ts`, `test-support.ts` being a sixth
construction site that `tsc` will not flag, the intermediate-ancestor fixture having to be seeded
through repositories, `ProjectPageService.list`'s workspace check and denied-path test, whether
`SectionQuery.pageId` resolves or filters, and acceptance check 3 needing the `mkdtemp` pattern
that `api/routes.test.ts` does not have today.

**Round 3** returned thirteen, four of them defects the round-2 revision introduced or left
standing — each of which would have produced a wrong answer rather than a visible failure.
Narrowing `isHidden` to `hasArchivedAncestor && !isArchived` was right for `ProjectService.list`,
`DashboardService` and `WorkspaceService` (the last two keep their own `status !== 'archived'`
filter, so the two are complementary) but wrong for `TaskService.list`, which has no archived
filter of its own and would have gone on leaking archived projects' tasks while the plan's table
said it did not; that row now uses `isArchived || isHidden` and says why it differs.
`SectionService.list`'s `includeArchived` branch is a direct repository read that never passes
through `ordered`, so the `orderedOnPage` split as written would have resolved a `pageId`,
refused a foreign one, and then answered with the whole project — it now branches on `pageId`
first and passes the filter into both branches. Two subtask paths place content while naming
neither a page nor a section — `resolveSection`'s `parentTaskId` branch and `update`'s reparent
branch — and neither of the disabled-page bullets reached them; both are now Refused, and the
Allowed side names cascade and `moveSubtree` so nothing is left to judgement. And
`resolveContainer` would have resolved the canonical page to search it and let `addWithin`

The rest were repairs to claims and one-line specifications: `assertNoActiveChildren` checks

### What changed after the plan

Two things the plan had wrong, both found in AGENTS.md §3 step 4 rather than in review of the
plan, and both worth stating here because the plan's own text argued for them.

**`SectionService.list` is page-scoped by default, not project-wide.** The plan reasoned
carefully about how a project-wide read should be *ordered* across pages, and never asked
whether it should exist. Running the feature answered that in one screen: enabling the
Reflections page and adding a container to it put that container on the **Home** canvas, and it
stayed there after the page was disabled — the one place a person can see, contradicting §27's
"hiding a page hides navigation, not data". A canvas *is* a page (§27), so a read that names
none answers the canonical one. The Archived region follows the same page, which is also what
§31 describes it as: the foot of a canvas. `byPageThenPosition` and the project-wide `ordered`
both went away with it, and no component changed — the existing callers pass no `pageId` and now
get the canvas they were always drawing.

**`archivedAncestry` no longer shares one walk's answer along its path.** The memoisation was
sound on a tree and wrong on a cycle, where "has an archived ancestor" stops being a property of
the chain and becomes relative to where the walk began: with `a → b → a` and `a` archived, `a`
has no archived ancestor and `b` does. Sharing made the ancestry answer differently for the same
project depending on which was asked about first, and disagree with `assertProjectWritable` —
producing the live-but-unreachable state the module exists to prevent, inverted. Each query now
walks its own chain and remembers only its own answer, which is O(depth) over a document already
in memory (§71). Both cycle tests in the plan used an all-live cycle and could not have caught
it; the replacement asks in both orders.

Smaller corrections from the same round: the type check now genuinely runs on both branches of
`resolvePage` rather than only the branch where it can fire; the page toggle route no longer
lets a request body name a different page kind than the path; `KIND_ORDER` reads §23's order
from `NAVIGABLE_PAGE_KINDS` rather than from `ProjectPageKind`'s own order, which agreed only by
coincidence; `README.md` and `docs/guides/mcp-setup.md` said "eighteen tools"; and two tests asserted
refusals they never staged — a `task-list` cannot reach a disabled page at all today, since the
only disable-able page that holds sections is Reflections, so the task-side guards are
uniformity rather than coverage and the tests now say what they actually prove.
